# PixelFlow 分析调度使用说明

本文说明 `pixelflow_intelligence.scheduled_maintenance` 周期调度包装器的部署与运维。
它复用单次有界维护入口 `maintenance` 的 `run`、配置校验和 HTTP 客户端约束，
在其上增加调度状态（画像扫描游标）、同目录进程互斥和稳定的退出码语义。
手动 CLI（`python -m pixelflow_intelligence.maintenance`）行为不变，见下文说明。

## 状态文件

默认目录 `/var/lib/pixelflow/python/maintenance`，可用
`PIXELFLOW_MAINTENANCE_STATE_DIR` 环境变量或 `--state-dir` 参数覆盖。
目录下：

- `state.json`：调度状态，JSON 格式，含 `version` 字段（当前为 `1`）：

  ```json
  {"version": 1, "refresh_after": "cursor-or-empty", "last_run_at": 1735689600, "last_status": "complete"}
  ```

  只记录画像扫描续跑游标和上次执行时间/结果，不含 token，不含用户明细。
- `.scheduled.lock`：锁文件，内容为持有进程 PID（O_CREAT|O_EXCL 创建）。
  启动时发现 stale PID（进程已不存在）会自动清理；崩溃后锁不会残留。

## 退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 本轮完整完成（complete），游标已重置为空，下轮从头扫描 |
| 2 | 达页数/时间预算仍有待处理（incomplete），游标已持久化，下轮从游标续跑 |
| 1 | 失败（配置非法、HTTP 非 200、响应异常、超时、中断等），游标不推进，可安全重放 |
| 3 | 另一进程正持有同一状态目录的锁，本轮未执行 |

标准输出为一行 JSON 日志，含 `status`、`complete`、`cursor_before`、
`cursor_after`、`cursor_advanced`、`duration`、`exit_code` 等字段；日志与
状态文件中都不会写入 token。

## 凭据

沿用 `PIXELFLOW_MAINTENANCE_URL`（默认 `http://127.0.0.1:8001`）与
`PIXELFLOW_INTELLIGENCE_TOKEN`（长度 ≥32 的可打印 ASCII）。两者放在
root 私有的 EnvironmentFile 中，命令行与 unit 文件里不得出现 token。

## 安装

unit 文件见 `deploy/systemd/pixelflow-analysis.service` 与
`pixelflow-analysis.timer`。在服务器上：

```bash
sudo install -m 0644 -o root -g root deploy/systemd/pixelflow-analysis.service \
    /etc/systemd/system/pixelflow-analysis.service
sudo install -m 0644 -o root -g root deploy/systemd/pixelflow-analysis.timer \
    /etc/systemd/system/pixelflow-analysis.timer

# 凭据文件：root 私有，同组 pixelflow 只读（systemd 以 root 读取后传给服务）
sudo install -m 0640 -o root -g pixelflow /dev/null /etc/pixelflow/analysis.env
sudoedit /etc/pixelflow/analysis.env
# 内容示例（写入真实值，不要提交到仓库）：
#   PIXELFLOW_MAINTENANCE_URL=http://127.0.0.1:8001
#   PIXELFLOW_INTELLIGENCE_TOKEN=<32 位以上 token>

sudo systemd-analyze verify /etc/systemd/system/pixelflow-analysis.service \
    /etc/systemd/system/pixelflow-analysis.timer
sudo systemctl daemon-reload
sudo systemctl enable --now pixelflow-analysis.timer
```

timer 在开机 2 分钟后首次触发，此后每 5 分钟触发一次（服务自身为
oneshot，timeout 180 秒，略大于单轮 120 秒预算；`SuccessExitStatus=2`
使分页截断不算服务故障；未配置自动重启循环）。

## 首次手动运行与手动触发一轮

```bash
sudo systemctl start pixelflow-analysis.service        # 手动触发一轮
sudo journalctl -u pixelflow-analysis.service -n 20 --no-pager
```

或直接以 pixelflow 用户运行（注意带上与 unit 一致的环境）：

```bash
sudo -u pixelflow env PIXELFLOW_MAINTENANCE_STATE_DIR=/var/lib/pixelflow/python/maintenance \
    /opt/pixelflow/current/intelligence/.venv/bin/python \
    -m pixelflow_intelligence.scheduled_maintenance --budget-seconds 120
```

输出为一行 JSON，例如
`{"entry": "scheduled_maintenance", "status": "complete", "complete": true, ...}`。

## 启停 timer 与查看日志

```bash
sudo systemctl start|stop pixelflow-analysis.timer
sudo systemctl list-timers pixelflow-analysis.timer
sudo journalctl -u pixelflow-analysis.service -f        # 服务输出（JSON 日志）
sudo journalctl -u pixelflow-analysis.timer -n 20       # timer 触发记录
```

## 失败重试语义

- 退出 1（失败）：只有成功返回的游标才会持久化。异常、超时、HTTP 非
  200、中断都不会推进游标，下轮（5 分钟后或手动触发）按原游标安全重放；
  内部重算接口是幂等的，重复执行不产生重复数据。
- 退出 2（未完成）：游标已推进到本轮实际扫描位置，下轮续跑，不跳页。
- 退出 3（锁忙）：通常无需处理；若长期出现，检查是否有残留进程
  （`systemctl status pixelflow-analysis.service`、锁文件中的 PID），
  stale PID 会在下次启动时自动清理。

## 状态文件备份与恢复（含损坏处理）

```bash
sudo cp -a /var/lib/pixelflow/python/maintenance/state.json /backup/maintenance-state.json
```

恢复时停掉 timer，放回备份文件，再启动即可；游标会决定从备份点续跑。
若启动输出 `CORRUPT_STATE_FILE`（state.json 不是合法 JSON 或 version
不匹配）：包装器不会静默清空也不会伪装成功。处理办法是从备份恢复；
若无备份且可接受从头扫描，删除 state.json 后重跑（下一轮的
`refresh_after` 为空即从头扫描）。

## 手动维护与调度入口的关系

手动触发统一走新包装器（`scheduled_maintenance`），它与 systemd timer
共用同一状态目录和锁：手动与定时不会并发执行同一状态目录，锁忙时
手动触发返回退出码 3。直接运行 `python -m pixelflow_intelligence.maintenance`
不受新锁约束（它不知道状态文件），也不会读写游标；仅适合一次性调试，
日常运维请使用包装器或 timer，以免两个入口互相看不到对方的游标进度。
