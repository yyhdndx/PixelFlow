# PixelFlow Android 端侧性能实验方案

日期：2026-10-18。状态：拟议实验，尚未实现测量模块或取得设备数据。研究依据与论文入口见[端侧性能研究调研](端侧性能研究调研.md)。

本方案用来保证后续测量可解释、可复跑，不是后端接口规范。具体机型待实验室资源确认；现在先固定问题、方法和验收条件。

## 1. 目标与范围

主问题：媒体信息流中，为未来内容提前执行的下载/解码任务，什么时候帮助前台，什么时候干扰前台？

第一阶段限定：

- Android 原有 Java/View 图片信息流；不同时改为 Compose。
- 固定顺序、固定素材和固定用户状态；不依赖推荐、Agent 或 Python 在线服务。
- 内容与媒体由可控环境提供；产品接口返回结构保持不变。
- 不改 ART、内核、CPU/GPU 频率、系统温控或 LMKD。
- 不以耗电、视频播放或跨 App 调度作为首轮主结论。

预期产出是：一个可重复的测量流程、一份瓶颈证据链、一组公平对照，以及在证据支持下实现的最小策略。不是预先保证“提速多少”。

## 2. 先登记研究问题与判断标准

| 问题 | 待检验假设 | 什么结果会削弱或否定它 |
|---|---|---|
| RQ1：内容等待由什么主导？ | 不同条件下，瓶颈会在传输、队列、解码与绘制之间迁移 | 各条件始终由同一阶段主导，则不必做多资源调度 |
| RQ2：预取是否干扰前台？ | 大窗口或高并发可能减少缺图，同时增加无用传输、内存和前台等待 | 修正基线后没有可重复的干扰，不应继续为该假设堆机制 |
| RQ3：分阶段与背压是否值得？ | 下载和解码分开、限制推测任务，可改善相同预算下的权衡 | 收益被合理固定窗口追平，或管理成本超过收益 |
| RQ4：能否迁移？ | 策略在不同轨迹、素材及设备条件下具有一致或可解释的趋势 | 只在调参轨迹有效，或更换设备后无法解释退化 |

正式比较前确定一个主要指标，例如“可见内容就绪延迟的运行级 P95”；同时指定正确性、失败率、流量、内存和帧表现为约束。不要看到结果后更换主要指标来挑选胜利。

这些假设和指标是本项目的实验设计，不是引用论文已经证明的结论。

## 3. 实验基线必须公平

### 3.1 策略变体

| 标识 | 定义 | 用途 |
|---|---|---|
| H0：历史实现 | 冻结当前工作区的预取行为和配置 | 展示工程历史，不作为唯一竞争基线 |
| B0：按需加载 | 关闭应用主动媒体预取，保留正常缓存、View 复用和按需请求 | 测量预取的净作用；不是“禁用所有缓存” |
| B1：合理固定窗口 | 修正明确缺陷；匹配展示规格；固定预取窗口、并发与取消规则 | 主对照；应在独立调参集选择合理窗口 |
| B2：仅数据预取 | 和 B1 使用相同候选，提前获取原始数据，显示时再解码 | 隔离提前传输与提前解码的影响 |
| B3：预算/时机感知 | 候选依据、传输/解码分阶段及资源准入策略 | 待验证的候选方法，不先假定优于 B1 |

第一轮无需实现全部变体。先用 H0、B0 和 B1 识别问题；有证据后再增加 B2、B3。

### 3.2 所有正式变体共享的条件

- 资源释放、会话隔离、请求去重、错误处理等正确性整改一致。
- 列表数据、布局、图片展示尺寸、裁剪方式和视觉质量一致。
- 同一 Glide/OkHttp 版本和相同基础缓存策略。
- 相同编译模式、压缩配置和测量开关；不拿 debug 与 release 互比。
- 业务行为上报要么全部保留，要么通过同一个实验开关全部关闭，并记录设置。关闭上报后的结果不代表完整产品性能。
- RecyclerView 自身的 View 预取与 Glide 资源预取分开记录；B0 不代表整个系统不存在任何预取。

Glide 预取与展示的尺寸和变换配置需要一致才能有效复用对应资源；原始数据缓存与变换后缓存要分别核查。固定窗口基线可以参考官方预加载做法，但当前是瀑布流布局，应核实滚动位置适配，不直接假定示例的布局条件成立。[Glide 预加载指南](https://bumptech.github.io/glide/int/recyclerview.html)

### 3.3 不把多项整改捆成一个“算法”

建议逐次记录：

1. H0 → 资源与缓存使用正确的基线：工程整改效果。
2. B0 → B1：普通主动预取效果。
3. B1 → B2：数据/解码阶段选择效果。
4. B1/B2 → B3：候选机制的额外价值。

如修复线程优先级、缩小图片、换播放器和新增调度同时发生，则不能把全部收益归因于其中一个机制。

## 4. 最小测量架构

建议新增的结构仅为后续实现草案，本次没有创建这些代码目录：

```text
macrobenchmark/                  固定操作旅程与性能测试
app/.../performance/             有界事件记录、场景标签、实验开关
app/.../prefetch/                可替换策略与统一执行/取消入口
tests/performance/               素材清单、场景定义、结果校验
scripts/performance/             设备信息采集、离线分析与报告
```

不要先搭建在线性能平台。使用本地实验目录保存 trace、结构化事件和结果，Python 离线分析即可。

### 4.1 建立事件关联，不复用业务曝光作为性能真值

每次运行至少记录：`run_id`、策略与配置、页面代次、内容 ID、资源 ID、请求 ID、是否推测请求、事件时间、结果与取消原因。

建议事件：

| 事件 | 定义 |
|---|---|
| `item_visible` | 根据 View 与 viewport 的几何交集达到预先规定的阈值；不是 attach 回调 |
| `item_hidden` | 离开上述可见条件；记录这一段可见区间结束 |
| `candidate_selected` | 被策略选为候选，尚不代表下载已经开始 |
| `request_enqueued` / `request_started` | 进入应用队列和实际交给执行层的时间 |
| `data_ready` | 原始数据可供后续读取，注明缓存或网络 |
| `resource_ready` | Glide 资源回调就绪，记录资源规格和 DataSource |
| `resource_bound` | 正确资源已绑定到仍对应同一内容的 View |
| `cancel_requested` / `request_terminal` | 请求取消与真正结束分开，终态包括完成、失败、取消 |
| `navigation_start` / `detail_content_ready` | 详情交互的明确起止点，不与 App 启动时长混用 |

记录 View 复用绑定代次，避免把上一项的迟到图片记为下一项加载成功；刷新、退出页面和账号切换同理。

### 4.2 时间与显示语义

- 使用设备单调时钟记录时长，例如 `elapsedRealtimeNanos`；不要用墙上时钟计算耗时。
- 应用事件与系统 trace 的时钟域必须核对，通过同步标记/clock 信息对齐；不能把不同来源的裸时间戳直接相减。
- `resource_ready` 或 `resource_bound` 是应用级代理事件，**不是像素已经出现在屏幕上的时刻**。
- 第一轮将指标命名为“内容就绪延迟”，不要声称测到了 touch-to-photon。
- 若要报告真实呈现时延，需要进一步把资源绑定与后续帧提交、呈现关联；无法唯一关联时披露误差，不编造精确值。

### 4.3 观测开销独立评估

准备三档采集：关闭研究采集、轻量计数/关键事件、详细诊断 trace。策略之间使用同档采集，并额外比较三档本身带来的差异。

事件缓冲有上限、溢出计数和批量写出机制；每帧不做 JSON 序列化、网络上报或同步磁盘写入。JankStats 的回调数据可被复用，需要及时复制必要字段，回调应快速返回。[JankStats 文档](https://developer.android.com/topic/performance/jankstats)

CPU 栈采样、分配分析、堆 dump 和详细 trace 可以在独立诊断轮次运行，不应全部同时开启后把结果当成“正常使用性能”。

## 5. 指标定义与误读防护

| 指标 | 计算与口径 | 注意事项 |
|---|---|---|
| 内容就绪延迟 | 对一次可见区间，计算 `max(0, t_bound - t_visible)`；已经绑定则为 0 | 只对对应资源/绑定代次计算；离开前尚未就绪的项单独处理 |
| 可见期间未就绪比例 | 未能在可见区间内就绪的区间数 / 总可见区间数 | 不能只删除这些样本再报告成功加载 P95 |
| 失败与超时率 | 失败/超时请求及受影响可见内容分别统计 | 更低延迟可能来自放弃困难请求，必须联合报告 |
| 帧表现 | 指定测量窗口内的 frame overrun 分布和所用工具的 jank 判定 | 按实际 deadline；不把 JankStats 与 FrameTimeline 的比例直接拼接 |
| 队列等待 | `request_started - request_enqueued` | 区分应用队列、网络调度与解码调度；不可只看 HTTP 服务时间 |
| 传输量 | 实际读取的响应体字节，分别归因于按需、推测及共享请求 | `Content-Length` 不代表实际传输了多少；重试/部分取消也有成本 |
| 预取有效性 | 在规定窗口内被前台消费的预取资源及其字节 | 区分命中、未用、尚未判定；不能将“请求完成”当命中 |
| 取消后开销 | 发出取消后仍发生的传输、解码或完成回调 | 用来验证取消是否真的传递，而非只取消外层 Future |
| 内存 | 固定采样方式的 PSS/RSS、Java/native 相关数据与诊断快照 | PSS、RSS、Java 堆、图形内存口径不同，不能简单相加 |
| 持续运行稳定性 | 重复旅程后内存、线程、队列和资源数量趋势 | 区分缓存预热后平台期与持续增长；增长不自动等于泄漏 |

Android Macrobenchmark 提供帧时间分布与启动指标；其中 `frameOverrunMs` 需 Android 12+。TTID/TTFD 是启动指标，不能直接替代任意图片或详情交互的就绪延迟。[指标定义](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)

关于未就绪样本：首轮可同时报告“成功就绪样本的延迟分布”和“未就绪比例、可见区间持续时间”。不能将未就绪记作 0，不能仅保留成功样本后声称整体更快；需要更严格时间到事件分析时再采用删失数据方法。

关于有效预取：同一内容反复回看、多个 View 共享请求、下载后才发起按需请求等情况，必须有唯一请求/资源关联。无法可靠归因的字节报告为 unknown，不按对策略有利的方式划分。应用层流量不是无线链路实际字节，更不能直接推出能耗。

进程内存和对象留存的解释应结合平台内存分类，而非只看 Java 堆大小。[Android 内存概述](https://developer.android.com/topic/performance/memory-overview)

## 6. 工作负载与可控条件

### 6.1 固定素材与数据顺序

- 第一轮使用已获许可的本地素材及固定内容清单，不在计时期间依赖外站 CDN。
- 清单包含内容 ID、资源哈希、字节数、像素尺寸、格式、长宽比和顺序。
- 数据量应足以覆盖若干屏并形成缓存压力；规模由预算与设备确认，不能把同一图片换多个帖子 ID 就当成大量独立资源。
- 不通过随机 query 强行绕缓存来制造优势；若测试缓存键行为，作为独立变量。
- 展示质量保持一致。低分辨率占位后换高清的策略，要另测质量与二次加载成本，不能无条件和全质量显示比较。

现有演示素材适合验证流程，但不能自动视为有代表性的性能数据集。

### 6.2 浏览轨迹

| 场景 | 操作 | 观察重点 |
|---|---|---|
| W1：慢速连续浏览 | 固定距离和节奏滚动，短暂停留 | 常规命中与内容等待 |
| W2：快速跳读 | 连续快滑后停在指定区域 | 无用预取、排队和停止后的内容补齐 |
| W3：反向回看 | 下滑后立即反向，再停留 | 取消、缓存污染与方向估计 |
| W4：进入详情再返回 | 在指定项进入详情，返回继续浏览 | 交互关键路径与生命周期资源回收 |
| W5：持续使用 | 重复完整旅程、切换前后台 | 内存/线程/缓存是否到达稳定区间 |

自动操作使用固定数据和稳定定位方式。记录实际完成的 item 路径和动作时间；相同 fling 命令在不同设备上不保证得到相同轨迹。脚本跑偏属于无效运行，依据预登记规则处理并保留失败记录。

### 6.3 网络条件

先使用三类条件：原始可控局域网、额外延迟、受限带宽。需要时再增加延迟与带宽组合、突发变化和失败注入。

例如附加约 80 ms RTT、限速约 2 Mbit/s 可以作为试验起点，但只是拟定压力条件，不代表真实 4G/5G 网络。用实际请求校验生效后的 RTT/吞吐，明确配置的是单向延迟还是往返延迟。

可以使用专用代理或 Linux 测试环境进行流量整形，避免要求 Android root。简单的服务器 `sleep` 只能模拟部分响应延迟，不能等同于低带宽、丢包和无线能耗。

普通业务 API 与媒体最好可分开控制；先冻结正常 API 延迟，只改变媒体条件。P08 的业务上报队首阻塞另做独立实验。Java 请求日志只用于校验服务端稳定性，不把后端冷启动混入端侧策略比较。

### 6.4 缓存条件

| 标识 | 条件 | 如何描述 |
|---|---|---|
| C0 | 本应用媒体内存与磁盘缓存为空 | 称“应用媒体冷缓存”，不称设备所有缓存都冷 |
| C1 | 预热磁盘数据、重启目标进程使内存缓存重新建立 | 称“磁盘暖、进程内存冷”，同时验证预热没有预先缓存全部变换资源 |
| C2 | 同进程重复旅程，保留内存与磁盘缓存 | 单独报告 warm path，不与 C0 混合 |

缓存操作只针对独立实验包及实验缓存，保留账号、业务数据和媒体原件。重启进程不等于清除系统页缓存；无 root 时尤其不能声称控制了全部 OS 缓存。不要为获得漂亮数据强制 GC 或任意清理设备内存。

## 7. 分阶段实验矩阵

避免一开始全排列“所有设备 × 所有策略 × 所有网络 × 所有缓存 × 所有轨迹”。

### E0：采集链路与噪声试验

同一版本、固定场景重复运行，先验证字段、trace、场景标记、时钟和脚本。检查关闭/开启采集的差异；依据方差决定下一阶段运行时长与重复数。

### E1：识别瓶颈

选择 H0/B0/B1，W1/W2，C0/C1，以及局域网和一种受限网络。先少量试跑，再对确有意义的单元增加重复次数。人工检查代表性慢样本和正常样本的 trace。

目的不是马上比较算法排名，而是定位等待发生在哪一层。

### E2：验证机制

固定同一批候选和总预算，比较 B1/B2/B3；增加 W3，观察分阶段与取消的作用。固定窗口至少测试几个合理值，再用独立轨迹验证选定参数，不只挑一个差窗口充当对照。

### E3：消融和泛化

逐个去掉“阶段分离”“预算限制”“前台优先”“方向变化取消”等实际存在的组件。不要为了消融而添加无关模块。再更换素材分布、轨迹和可用的第二台设备，保留真实退化结果。

### E4：视频或平台扩展

仅在前三阶段完成后选择一个扩展：

- 视频：区分封面抽帧、播放首帧、重缓冲、播放器池与解码器占用；FrameTimeline 的窗口帧不是视频 QoE 的替代品。Media3 提供分析接口，但当前项目使用旧 ExoPlayer，迁移要独立验收。[播放器分析文档](https://developer.android.com/media/media3/exoplayer/analytics)
- root 对象分析：确认 DroidPerf 的设备与事件支持，单独估计分析器开销。
- 平台复现：在 artifact 指定环境建立 Android/Fleet 等系统对照，重新设计多 App 工作负载，不沿用单应用实验来证明平台结论。

## 8. 候选策略的实现要点

以下是 E2 的机制草案，不是已经实现或证实的新算法。

### 8.1 统一请求所有权

资源请求用稳定资源身份及展示规格区分；业务“优先级”应是请求属性，不应随意成为让同一底层资源重复下载的身份部分。

如果预取请求已经被可见 View 消费，应提升其服务等级或复用结果，而不是取消后重新下载。多个消费者需要明确引用关系；最后一个消费者离开后才考虑底层取消。

取消、完成和 View 复用存在竞态，必须有终态与代次校验。不要把回调到达晚于页面退出视为一定加载失败，也不要让它继续更新旧页面。

### 8.2 分阶段准入

把候选按粗略的预计可见时间排序，并估计近期传输和解码成本。在约束允许时提前取原始数据；对很远或不确定的候选，延后解码。

估计值不要求一开始很复杂：滚动速度平滑、最近同尺寸图片耗时、窗口内有效预取比例即可。需要处理静止、加速、反向和数据不足，不能除以接近零的速度或假定轨迹永不变化。

如果使用 Glide 的数据获取/预加载能力，应先做一个微型验证：数据预取后展示是否命中期望缓存层、是否仍发生重复传输/解码、Target 是否正确释放。不要为了分阶段重写成熟图片解码器。

### 8.3 预算与背压

至少区分三个量：在途推测请求数、推测传输预算、预解码资源的估计空间预算。

“限制自建包装线程池”不等于限制 Glide 内部工作并发；应验证准入点是否真的控制了目标资源。回调、队列与已完成缓存也需要上限，否则只是把压力转移位置。

`宽 × 高 × 每像素字节数` 只能作粗略像素空间估计；配置、对齐、硬件 Bitmap 和 native/图形分配会影响实际占用。预算是可测的控制变量，不是精确物理内存计量。

前台请求优先不等于无限提高线程优先级。先用准入、并发限制和取消减少竞争，再观察是否还有调度问题。不能依赖新版系统不再保证发送的旧内存回调来维持预算。[内存回调兼容性](https://developer.android.com/reference/android/content/ComponentCallbacks2)

## 9. 因果分析与统计约定

### 9.1 证据链模板

每一个瓶颈结论保存以下内容：

1. **现象**：哪个场景、哪个指标、多少次运行出现。
2. **时间定位**：问题在哪个 request/item/帧区间。
3. **候选原因**：例如队首阻塞、重复解码、主线程布局、调度等待。
4. **替代解释**：网络波动、温控、缓存预热、脚本跑偏等。
5. **干预**：一次只改变一个能区分原因的因素。
6. **复测**：相同条件重跑，观察预测是否成立。

示例：详情慢，HTTP 服务时间却正常 → 检查请求在应用串行队列中的等待 → 只对上报注入延迟 → 检验详情等待是否随之变化。单纯看到 CPU 某线程很忙，不能证明它导致详情慢。

### 9.2 重复与汇总

- 以完整浏览运行/会话作为重复单元，帧和图片是其中的相关样本；不能把一台手机的一万帧当作一万个独立实验。
- 先用少量 pilot 估计方差，再决定正式重复数。可以从每条件约 10 次 pilot、重要条件约 20—30 次正式运行开始，但这不是统计充分性的保证。
- 在同一设备、网络和缓存条件下交错或随机化策略顺序，避免 B3 永远在设备更热或缓存更暖时执行。
- 每次运行计算延迟分位数、未就绪率、流量与内存，再比较运行级结果；不要把所有设备和运行的样本直接混成一个 P95。
- 报告绝对差、相对差和运行级不确定性；可使用按运行重采样的置信区间。接近零的基线不报夸张百分比。
- 调参轨迹与评估轨迹分离。设备很少时按设备分别呈现，不宣称代表全部 Android 设备。
- 运行不完整、过热、trace 丢失等排除条件提前登记，保存排除理由与数量。负面和无效实验不能无声删除。

### 9.3 推荐报告图表

只生成能够回答问题的图：

- 延迟—传输量的权衡图，按内存预算或策略分组。
- 同一工作负载下的运行级尾延迟与未就绪率。
- 代表性慢请求的阶段时间线，与系统调度/帧信息对齐。
- 持续运行时内存、队列与线程数量曲线。
- 消融结果及至少一个策略退化场景。

缓存、GC、网络、解码和渲染可能重叠；不可把重叠阶段画成严格相加的总耗时分解，再据此计算“贡献比例”。

## 10. 数据保存与安全

每个 `run_id` 至少保存：

- Git 提交号、dirty 状态、未提交代码快照标识、APK SHA-256、依赖与策略配置。
- 机型、SoC、RAM、Android 版本/build fingerprint、实际刷新率、屏幕亮度、温控/供电状态。
- 内容清单哈希、轨迹版本、网络配置与校验结果、缓存准备方式、编译模式。
- 原始 trace、结构化应用事件、汇总结果、运行有效性与排除原因。
- 分析脚本版本、工具版本、数据缺失与观测开销信息。

元数据中的隐私字段需要最小化：不要保存真实用户令牌、密码、完整用户帖子内容、个人文件路径或设备序列号。用测试账号、素材 ID 和必要哈希；分享 trace 前审查进程名、路径和日志内容。

研究采集不要同步上传到业务 `/api/events`，避免污染用户画像并引入新的请求竞争。实验原始数据默认保存在专用本地目录，不直接加入 Git；只提交脚本、清单、脱敏汇总与必要的小样本。

不得为实验清空整个手机、关闭系统安全机制或自动解锁设备。刷机/root 属于以后单独确认的研究操作，本方案不授权执行。

## 11. 设备能力分级：等实验室资源确认后再落到型号

| 级别 | 可开展的工作 | 资源确认时检查 |
|---|---|---|
| A：普通可调试真机 | 自有 app 基准、轻量事件、系统 trace、部分 CPU/内存分析 | Android 版本、ADB、profileable 构建、实际可用数据源、刷新率控制 |
| B：有 root 的专用真机 | 对象/硬件事件分析、更多系统数据访问 | root 是否允许、PMU 事件支持、工具兼容、可恢复镜像 |
| C：可解锁且有 AOSP/内核构建条件 | Fleet 等平台机制复现 | artifact 目标机型、系统版本、驱动、Linux 构建资源、刷写与恢复方案 |
| D：有可靠功耗测量条件 | 能耗与性能权衡 | 设备支持的测量方式、系统与 app 归因、外部供电和校准 |

等级不是线性优劣：A 级也能完成严谨的应用/系统交界处研究，D 级也不能自动解决因果归因。先不采购，不要求实验室必须提供某个特定型号。

Macrobenchmark 的模拟器结果不代表终端性能；正式数据需要真机。heapprofd 在零售系统上对自有 app 的分析能力取决于 profileable/debuggable 标记，不等于可以分析任意其他应用。[基准教程](https://developer.android.com/codelabs/android-macrobenchmark-inspect)、[heapprofd 权限说明](https://perfetto.dev/docs/data-sources/native-heap-profiler)

## 12. 后续可以逐条创建的任务

每条以一个可验收结果为单位，不一次性生成大套接口规范。本次仅列候选任务，没有实际创建 Issue。

| 顺序 | 任务 | 完成标准 |
|---|---|---|
| 1 | 固定实验范围和素材/轨迹 | 能重复得到相同内容顺序，区分图片、视频和业务上报 |
| 2 | 建立 release-like 基准构建与一个滚动旅程 | 在设备可用后运行，产出有配置和标识的结果；当前可先准备测试结构 |
| 3 | 增加轻量资源与队列事件 | 请求、内容、绑定代次可关联，缓冲有界，有丢事件计数 |
| 4 | 形成 H0/B0/B1 并验证正确性 | 对照条件一致，修复不被算入新策略贡献 |
| 5 | 完成首次关键路径报告 | 至少一个可重现现象及受控干预证据，允许结论为“暂无明显瓶颈” |
| 6 | 决定是否实现 B2/B3 | 只有预取/资源竞争证据支持时继续；否则改题或停止 |
| 7 | 消融与跨条件验证 | 报告资源成本、退化条件及不确定性 |
| 8 | 决定是否复现平台 artifact | 根据实验室设备与指导条件另行立项 |

最终验收不是“多写了一个 PreloadManager”，而是能回答：现象是什么、原因证据是什么、机制为什么有效或无效、结论在什么条件下成立，以及别人如何重跑实验。
