# Android 端侧性能研究调研与选题建议

调研日期：2026-10-18。对象：PixelFlow Android 客户端。配套执行文档：[端侧性能实验方案](端侧性能实验方案.md)。

设备约定：具体机型待实验室资源确认，本轮不选型、不采购，也不要求解锁或刷机。以下按能力分级讨论，不把设备信息未定视为调研阻塞。

本文回答三个问题：哪些 Android 性能问题值得深入研究；哪些论文与工具能够提供可复现的入口；怎样把社区应用变成可信的实验载体。本文不是接口规范，也不是已经取得性能提升的报告。

## 1. 结论与研究边界

建议采用“先测量与归因，再选择机制”的路线。第一候选题为：

> Android 媒体信息流的内容就绪关键路径与推测性工作干扰：面向显示时机和资源预算的预加载研究。

这里的“推测性工作”是指为用户可能浏览、但尚未真正需要的内容提前下载或解码。研究重点不是笼统地增加缓存，而是判断：提前工作在什么时候缩短等待，在什么时候反而争抢网络、CPU、内存或磁盘资源。

推荐理由：

- 信息流、图片、详情切换提供了自然的交互工作负载，不需要为了研究另造一套产品。
- 可以从普通真机和自有应用开始，不以 root、刷机或更换系统为前提。
- 能深入线程调度、渲染时限、图片解码、内存与 I/O，而不只停留在页面代码。
- 能设计明确的对照、消融和失败场景；即便优化没有收益，也可以得到有意义的测量结论。

这个题目是本项目的候选研究设计，不是已经确认的新颖贡献。若测量发现主要瓶颈是布局或业务队列，而非预加载，应调整题目，不能为了预设方案筛选结果。

### 1.1 三个层次，不混称“系统研究”

| 层次 | 主要工作 | 对当前项目的建议 |
|---|---|---|
| 工程整改 | 修复生命周期、资源释放、错误线程优先级等问题 | 必须做，但单独列为基线治理，不包装成研究创新 |
| 应用与系统交界处的研究 | 研究可见内容的关键路径、任务竞争、缓存和内存的权衡，用系统 trace 验证 | 主路线，适合当前阶段 |
| Android 平台机制研究 | 修改 ART、内核换页、系统调度或图形框架 | 有独立设备、构建环境和指导条件后另立课题 |

“深入”应体现为能解释机制、排除替代原因、说明边界，而不等于修改的系统层级越低越好。应用层实验不能声称已经改进了 Linux 调度器或 ART 垃圾收集器。

### 1.2 不增加项目范围

- 不建设 Web；实验报告、图表和 trace 是研究产物，不是管理端功能。
- 不要求先完成推荐、Agent、Skill、MCP；实验时冻结内容顺序，避免模型输出成为干扰变量。
- Java 主要提供稳定的内容与媒体；分析脚本可以用 Python 离线运行，不要求新建性能分析在线服务。
- 第一轮只研究图片信息流。视频封面抽帧和实际视频播放分别列为扩展工作负载，不能混入第一轮后一起解释。
- 暂不引入强化学习、大模型调度器或全面 Compose 重写。

## 2. 本次调研的证据范围

本次进行了论文与官方文档检索、作者公开仓库检查，以及项目相关源码静态检查。选取 2012—2026 年与预取、追踪、内存和调度直接相关的代表工作；这是一轮定向调研，不是穷尽式系统文献综述。

证据分为四类：

1. **已确认的项目事实**：能从当前源码直接看到的配置和控制流程。
2. **文献事实**：由作者、出版方、会议网站或官方工具文档支持的机制与前提。
3. **待验证假设**：对项目运行时瓶颈的推断，必须经过设备实验。
4. **拟议设计**：本文建议的实验和机制，不代表已有实现或已证实有效。

源码检查对应 `HEAD=ec4792c` 及 2026-10-18 的工作区修改；工作区存在大量未提交改动，不能仅用这个提交号重建本次看到的代码。正式实验须保存 APK 哈希、配置和完整源码快照信息。

本次没有运行论文 artifact、刷写设备、采集真机 trace 或得到性能数值。部分出版方全文访问受限：相关条目依据可检索的出版摘要、方法片段及作者仓库，不能视为全文复现实验已经核验。

## 3. 研究对象：从“卡”拆成不同机制

一张信息流图片的显示可以粗分为：

```text
内容被需要 / 进入可见区域
  → 应用请求排队 → 数据读取或网络传输
  → 解码、缩放、变换 → 绑定 View、布局与绘制
  → RenderThread / GPU / 合成 → 显示
```

这是依赖关系示意，不是各阶段严格串行、耗时可以直接相加的公式；缓存命中与并发会改变路径。

至少分清以下问题：

| 现象 | 可能原因 | 不能直接下的结论 |
|---|---|---|
| 图片一直是占位图，但滚动流畅 | 网络等待、任务排队、未及时发起请求 | 不能称为渲染掉帧 |
| 图片都加载好了，滑动仍卡顿 | 布局、主线程计算、纹理上传或调度等待 | 不能继续盲目增加预取 |
| CPU 占用不高，页面却很慢 | 锁等待、I/O、业务队列、线程 runnable 但未运行 | 不能认定没有 CPU/调度问题 |
| 返回页面更快，但内存上升 | 留存缓存、播放器、Bitmap 或页面对象 | 不能只报速度而忽略空间成本 |
| 长时间使用后退化 | 数据集增长、资源未释放、GC、温控或系统压力 | 不能仅凭相关时间点认定“内存泄漏” |

Perfetto 的 FrameTimeline 区分预期与实际帧时序，并提供不同的 jank 类型；它要求 Android 12 及以上，且不能替代应用内部原因分析。不能一律用“超过 16.67 ms”判断所有刷新率设备的卡顿。[FrameTimeline 官方文档](https://perfetto.dev/docs/data-sources/frametimeline)

## 4. 代表研究与复现可行性

以下按研究问题组织，不按会议排名挑题。公开源码只证明有检查入口，不证明依赖可安装、设备兼容或结果能重现。

### 4.1 预取：选择什么、何时执行、付出多少成本

| 工作 | 核心机制 | 公开材料与复现判断 |
|---|---|---|
| IMP：Informed Mobile Prefetching，MobiSys 2012 | 根据预取收益和资源成本进行决策，考虑流量与能耗预算 | 作者提供 Android 库；依赖旧 NDK/Eclipse 时代组件和能耗库。适合学习成本收益思想，原环境复现成本较高。[作者仓库](https://github.com/brettdh/informed_mobile_prefetching) |
| PALOMA：Leveraging Program Analysis to Reduce User-Perceived Latency in Mobile Applications，ICSE 2018 | 用程序分析识别可以预取的请求及触发位置 | 项目页提供分析器、代理和测试基准入口。若主攻静态分析值得复现；对当前媒体资源调度题，自动插桩不是第一优先级。[作者项目页](https://felicitia.github.io/PALOMA/) |
| NAPPA：Navigation-aware and Personalized Prefetching of Network Requests in Android Apps，ICSE 2019 NIER | 用扩展导航图描述 Activity 转移和候选请求 | 有库、插件和测试应用。适合作为方法复现入口；导航请求预测不等于同一页面内的图片解码调度。[作者仓库](https://github.com/S2-group/NAPPA)、[会议条目](https://2019.icse-conferences.org/details/icse-2019-New-Ideas-and-Emerging-Reults/18/Navigation-aware-and-Personalized-Prefetching-of-Network-Requests-in-Android-Apps) |

对 PixelFlow 的启发：预测命中率不是唯一目标，需要同时回答“预测到了以后，是否应该现在占用资源执行”。例如远处图片值得先下载，但未必值得立即解码成大 Bitmap。

复现命名须准确：如果没有实现 PALOMA 的程序分析或 NAPPA 的导航机制，只是写了滚动窗口预加载，应称为“参考相关工作设计的策略”，不能称为上述系统的复现。IMP 的作者 PDF 入口本次访问失败，不能据此声称已核验其全文实验。

### 4.2 可观测性：异常发生前，能否留下足够证据？

**Hubble，OSDI 2022。** 通过运行时插桩把方法事件写入内存环形缓冲，在检测到性能异常时保留相关记录。关键思想是同时考虑持续观测的开销和异常前信息，完整系统还涉及运行时和低开销实现，不是普通应用加几个日志。[会议介绍](https://www.usenix.org/conference/osdi22/presentation/luo)、[论文原文](https://www.usenix.org/system/files/osdi22-luo.pdf)

**XTrace，ICSE 2026 SEIP；预印本发表于 2025 年。** 研究基于 ART instrumentation 的动态追踪，关注覆盖率、执行模式与线上稳定性。可读取论文方法，但本次未确认作者可运行 artifact；同名 `google/xtrace` 是 Android XR 的追踪工具，不是这篇论文实现。[会议条目](https://conf.researchr.org/details/icse-2026/icse-2026-software-engineering-in-practice/74/XTrace-A-Non-Invasive-Dynamic-Tracing-Framework-for-Android-Applications-in-Producti)、[原文](https://arxiv.org/html/2512.21555v1)

本项目可以借鉴“有限开销下保留异常前上下文”的思路：记录请求排队、可见内容、取消、解码完成等应用事件，与系统 trace 对齐。若只做这些，准确定位是应用级测量工具，不是 Hubble/XTrace 的完整复现。

如果后续真正把观测工具作为研究主线，就要评价证据覆盖率、丢事件率、CPU/内存/落盘开销，以及能否帮助定位不同类型的问题，不能仅展示一张漂亮时间线。工具路线与预加载路线可共用测量基础，但不应同时承诺两个完整研究贡献。

### 4.3 对象与内存：内存“占得少”不等于“用得有效”

**DroidPerf，MobiCom 2023。** 将内存低效与对象联系起来，研究对象分配、访问与局部性。会议材料和公开代码提供了较明确的学习入口；仓库使用说明明确要求设备 root，验证平台写明 Pixel 7，不能理解为任意零权限 APK 可直接使用。[会议报告](https://www.sigmobile.org/mobicom/2023/media/presentations/LiDroidPerf.pdf)、[作者代码](https://github.com/Xuhpclab/DroidPerf)

对项目的实际意义：先区分 Java 对象、native 分配、图形相关内存和进程总占用，再研究对象生命周期与访问。图片 decode、缓存命中和 GPU 上传不是同一个事件；减少 Java 堆占用不保证减少总内存或减少掉帧。

如有专用可 root 设备，可以把 DroidPerf 作为第二阶段候选；当前无 root 路线先使用系统 trace、分配采样与堆快照进行分析。使用堆分析发现问题属于方法借鉴，不等于复现了 DroidPerf 的对象归因机制。

### 4.4 ART 与内核协同：真正的平台研究，需要独立环境

| 工作 | 研究的问题 | 当前适合程度 |
|---|---|---|
| Marvin：End the Senseless Killing，USENIX ATC 2020 | 语言运行时和换页协同，降低内存压力下的回收与恢复成本 | 适合学习 GC 与 swap 的相互影响；不适合作为应用内小改造。[论文入口](https://www.usenix.org/conference/atc20/presentation/lebeck) |
| Fleet：More Apps, Faster Hot-Launch…，ASPLOS 2024 | 结合前后台对象访问特征协调 GC 与 swap，平衡后台驻留和热启动 | artifact 包含 AOSP、内核和评测脚本，说明使用 Android 10／Pixel 3；是有条件的平台复现候选。[作者所属机构条目](https://scholars.cityu.edu.hk/en/publications/more-apps-faster-hot-launch-on-mobile-devices-via-forebackground-/)、[作者代码](https://github.com/jiachengh/Fleet) |
| Silk：Runtime-Guided Memory Management…，ACM TACO 2026 | 通过运行时对象热度指导页面组织与回收，分别考虑应用和 GC 工作集 | 可用于追踪近期研究趋势；本次没有确认可直接复现的公开代码与完整设备配方。[出版方条目](https://doi.org/10.1145/3760785) |

这条线需要理解 ART 堆与 GC、页级回收、缺页、zram/swap、LMKD 和前后台切换。PixelFlow 可以成为其中一个工作负载，但不能仅凭单应用证明整个系统更优。

Fleet 的脚本还涉及调整系统安全检查、LMKD 和换页配置。只能在专用测试设备上审查后操作，不能照抄到日常手机；本次未执行任何相关脚本。Android 10 的内存机制结论也不能无条件推广到当前系统。

### 4.5 CPU/GPU 调频：研究价值高，第一阶段不合适

**MobiRL：An Intelligent Scheduling Approach on Mobile OS for Optimizing UI Smoothness and Power，ACM TACO 2025。** 使用强化学习调整 CPU/GPU 频率配置，其实现涉及 `system_server` 和系统状态采集、调频权限。它的 agent 是强化学习控制器，不是大模型工具调用 Agent。[出版方条目](https://doi.org/10.1145/3674910)

普通应用调整自己的工作队列，不能声称复现了这种系统调频。也不建议为了“AI + 系统”直接使用大模型调度每帧工作。正式研究频率与功耗前，需要设备权限、测量条件、温控管理和对商业调度器的认识。

### 4.6 文献选择后的决策

| 路线 | 普通真机起步 | 与当前代码结合 | 主要风险 | 建议 |
|---|---|---|---|---|
| 关键路径测量与瓶颈归因 | 可，自有 app 配置需验证 | 很高 | 测量扰动、误判因果 | 必做基础 |
| 预算与显示时机感知预取 | 可 | 很高 | 基线不公平、收益被缓存条件混淆 | 第一候选研究题 |
| 低开销异常上下文记录 | 可做应用级版本 | 高 | 把日志系统误称为创新 | 备选主线 |
| 启动与 Baseline Profiles | 可 | 中 | 工程收益明显但研究问题较弱 | 小型测量练习 |
| DroidPerf 对象级分析 | 公开用法要求 root | 中高 | 硬件事件、系统版本、工具自身开销 | 有设备后进阶 |
| Fleet/Marvin/Silk | 通常需平台修改环境 | 作为负载，中 | 刷机、构建、版本迁移、缺少 artifact | 导师与设备支持后开展 |
| MobiRL 式系统调频 | 需系统级条件 | 低至中 | 功耗测量与训练成本 | 暂不开展 |

## 5. PixelFlow 源码中的研究切入点

以下是静态观察，不是已经通过 trace 确认的瓶颈。位置用方法名定位，避免随修改失效的行号。

### 5.1 当前实验基础

Android 使用 Java/View、RecyclerView 瀑布流、Glide 4.16.0、OkHttp 4.12.0、Room 2.6.0 和 ExoPlayer 2.16.1；构建配置为 AGP 8.5.0、compile/target SDK 34、min SDK 24。版本来自仓库，不代表推荐的最新版本。

目前 Gradle 仅包含 `:app`，没有独立 Macrobenchmark 模块；release 未开启代码压缩。研究前可以新增实验构建与测量模块，但不要同步全面升级 UI、播放器、依赖和业务架构，否则无法归因。

源码入口：[构建配置](../../app/build.gradle.kts)、[依赖版本](../../gradle/libs.versions.toml)、[模块配置](../../settings.gradle.kts)。

### 5.2 静态线索、机制假设和验证方式

| 编号 | 已确认的源码事实 | 待检验的问题 | 验证方式 |
|---|---|---|---|
| P01 | `HomeFragment` 在整页数据到达后预取 `unique`，滚动时又预取相邻约 3 项 | 不同入口是否重复调度、使远处内容挤占可见请求 | 区分候选、真正启动、合并、命中和取消，观察网络/解码队列 |
| P02 | `PreloadManager.getTargetSize` 按优先级使用缩小尺寸；展示请求使用目标尺寸及 `centerCrop` | 预取是否只复用了原始数据，却没复用解码/变换结果 | 记录请求规格、Glide `DataSource`、解码活动及显示等待 |
| P03 | 预取调用 `submit(...).get()`，未保存对应 Glide Target 用于明确清理；取消主要面向外层 `Future` | 取消外层等待后，底层加载是否继续，资源何时可回收 | 检查 Target 生命周期、取消传播、迟到回调与网络完成记录 |
| P04 | 两个线程池的核心线程数来自可用 CPU 数，最大线程数不一定限制为 4 | 工作线程是否过多，或只是阻塞等待 Glide 内部线程；实际解码并发由谁控制 | 同时观察包装线程池与 Glide 线程，测排队、运行、等待时间 |
| P05 | `Thread.NORM_PRIORITY-1` 和 `Thread.NORM_PRIORITY` 被传入 `Process.setThreadPriority` | 标记为“高”的线程得到 nice 5，普通为 4，数值语义与命名不一致；实际关键工作又可能在 Glide 线程上 | 核实系统优先级和实际执行线程，不能只改常量就宣布优化 |
| P06 | `preloadCache` 存储记录，每项计 1；清理记录不等于清理 Glide 的图片资源；`optimizeCache` 为空 | 记录上限是否与实际内存预算脱节 | 联合测量进程内存、Bitmap/分配数据和请求生命周期 |
| P07 | `onTrimMemory` 主要依赖旧的运行中内存压力等级 | 新 Android 是否会提供预期的触发信号 | 区分版本能力，不能把人工调用回调当作真实系统内存压力 |
| P08 | `CommunityClient` 的业务请求与行为上报进入同一个串行执行器；上报最多挂起 1 个，请求有 3 秒上限 | 有界上报仍可能造成详情请求的队首阻塞 | 分别记录入队时间、实际发起时间和响应时间，在上报慢响应下对照 |
| P09 | `ProfileFragment` 在选择图片回调中先解码原图再缩放 | 大图头像是否造成主线程停顿和内存峰值 | 独立的大图导入用例，不混入信息流主实验 |
| P10 | `SplashActivity` 包含淡入、停留、淡出的显式计时 | 启动时长是否主要来自产品动画而非代码执行 | 分开报告启动首帧与首页内容可用；不要把删等待算作 ART 优化 |
| P11 | `ImagePagerAdapter` 维护最多 3 个播放器的池 | 复用带来的首帧收益是否伴随额外 native/解码器资源 | 留到视频扩展，单独记录首帧、重缓冲与内存 |
| P12 | 列表用 `onViewAttachedToWindow` 近似记录曝光 | attach 是否被误用为真实可见或内容已经显示 | 研究数据另设几何可见性和资源就绪事件，不直接复用业务曝光日志 |

源码：[首页](../../app/src/main/java/com/PixelFlow/app/ButtonFragment/HomeFragment.java)、[预取管理](../../app/src/main/java/com/PixelFlow/app/Streams/PreloadManager.java)、[列表适配器](../../app/src/main/java/com/PixelFlow/app/Streams/WaterfallAdapter.java)、[网络队列](../../app/src/main/java/com/PixelFlow/app/API/CommunityClient.java)、[个人页](../../app/src/main/java/com/PixelFlow/app/ButtonFragment/ProfileFragment.java)、[启动页](../../app/src/main/java/com/PixelFlow/app/SplashActivity.java)、[媒体适配器](../../app/src/main/java/com/PixelFlow/app/DetailPage/ImagePagerAdapter.java)。

支撑上述判断的库与平台语义：

- Glide 的解码/变换缓存键包含尺寸、变换等因素；预取和展示配置应匹配。尺寸不匹配不意味着所有层的缓存都失效，应区分原始数据与变换后资源。[缓存机制](https://bumptech.github.io/glide/doc/caching.html)、[预加载指南](https://bumptech.github.io/glide/int/recyclerview.html)
- 加载完成也不代表可以忽略 Target 的清理；但仅凭缺少 `clear` 不能断言已经发生某种规模的泄漏。[Target 生命周期](https://bumptech.github.io/glide/doc/targets.html)
- Android 线程 nice 值越小优先级越高，与 Java 线程优先级的常见数值理解不同。[Process API](https://developer.android.com/reference/android/os/Process#setThreadPriority(int))
- 多个 `TRIM_MEMORY_RUNNING_*` 等级自 API 34 起不再通知，相关常量在 API 35 废弃；不能把这些回调作为唯一资源预算机制。[ComponentCallbacks2](https://developer.android.com/reference/android/content/ComponentCallbacks2)

### 5.3 避免弱基线

保留当前实现作为工程历史基线，但必须另建“修正明显缺陷、使用合理缓存和取消策略”的基线。新策略主要与后者比较。

否则，新版本如果仅修复缓存键不匹配、资源清理或错误优先级，就可能看起来大幅提升，但证明的只是旧实现有问题。报告应把“整改收益”和“新策略增量收益”分开。

## 6. 主路线的研究问题与候选机制

### 6.1 可证伪的问题

- **RQ1：等待来自哪里？** 在冷/热缓存、慢滑/快滑、不同网络条件下，可见内容的尾延迟由哪些阶段主导？
- **RQ2：何时预取得不偿失？** 增加窗口或并发度，在什么时候缩短内容等待，又在什么时候增加无用下载、主线程/解码竞争或内存压力？
- **RQ3：分阶段与背压是否有帮助？** 把提前取数据与提前解码分开，并优先满足可见内容，能否在相同资源预算下改善延迟—开销权衡？
- **RQ4：结论是否可迁移？** 换设备、内容大小和浏览轨迹后，收益是否仍存在？若只在一个设备或一种轨迹成立，应如何解释？

“背压”指下游解码、内存或前台请求已经拥塞时，限制新的推测性工作进入，而不是无限排队。

### 6.2 最小候选机制

先不训练模型，使用可解释的小策略：

1. 估计内容距可视区域的距离和近期滚动速度，得到粗略的“可能需要时间”，并处理停顿、反向和不确定性。
2. 区分 `候选 → 数据预取 → 可选解码 → 被显示/失效`，不要求每个候选立即完成全部阶段。
3. 对推测性任务设置并发、传输字节和已解码资源预算；可见请求应有明确优先权。
4. 快速反向、刷新或页面销毁时传播取消；不能取消已经被前台共享的同一个请求。
5. 记录命中、浪费和成本，用历史观测调整窗口；保留固定窗口作为低复杂度对照。

这只是候选机制，不保证比 Glide 的合理预取配置更好。真正研究的不是增加状态机本身，而是它能否解释并改善可重复出现的资源冲突。

### 6.3 有研究价值的产出

- 一套能重跑的场景、素材清单、设备配置与原始结果。
- 对两个以上瓶颈的证据链：现象、trace、候选原因、单因素干预、重新测量。
- 与合理基线相比的权衡曲线，而非只给一个“提升百分比”。
- 至少一次消融和一个无收益/退化场景。
- 说清适用范围的技术报告。若只有工程收益或负结果，就按事实报告。

要继续发展为论文，还需进一步检查相邻工作、在更多负载中验证机制，并与导师讨论贡献；本调研不能保证发表级新颖性。

## 7. 测量工具与环境门槛

| 工具 | 用来回答什么 | 条件与限制 |
|---|---|---|
| Macrobenchmark + UI Automator | 相同操作脚本下的启动、滚动和交互性能 | 使用非 debuggable、可分析的实验构建和真机；与 debug 功能测试分开。基准依赖版本需和当前构建链验证。[官方指南](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview) |
| Perfetto + FrameTimeline | 帧时序、调度、主线程/渲染线程和 I/O 等证据关联 | FrameTimeline 需 Android 12+；具体 trace 数据源与 OEM 权限有关，不保证所有 GPU/系统事件可见。[官方文档](https://perfetto.dev/docs/data-sources/frametimeline) |
| JankStats | 将帧问题关联到页面、滑动和加载状态 | 是应用内诊断补充，不能直接把其启发式 jank 判定与 FrameTimeline 混为同一个指标；回调必须轻量。[官方文档](https://developer.android.com/topic/performance/jankstats) |
| Simpleperf | CPU 执行热点与调用栈 | 采样、符号和硬件事件权限需实机确认；CPU 热点不等于 I/O 或锁等待原因。[AOSP 文档](https://android.googlesource.com/platform/system/extras/+/master/simpleperf/doc/README.md) |
| heapprofd、堆快照、进程内存统计 | 分配热点、对象留存、native 和总内存变化 | heapprofd 需 Android 10+，零售系统对目标 app 的 profileable/debuggable 标志有要求；堆快照不放在主性能计时段。[官方说明](https://perfetto.dev/docs/data-sources/native-heap-profiler) |
| Baseline Profiles | 编译状态对关键路径的影响 | 是工程工具而非自动形成研究题；必须控制各变体的编译状态。[官方概述](https://developer.android.com/topic/performance/baselineprofiles/overview) |
| ProfilingManager | 应用发起的系统分析请求 | 基础 API 35+，系统触发器 API 36+，请求可能限流或不执行；当前 compile SDK 34 不能直接照搬新 API。[API 文档](https://developer.android.com/reference/android/os/ProfilingManager) |
| PowerMetric 或外部功耗仪 | 能耗/功率权衡 | 指标可用性受设备限制，系统级耗电不直接等于本 app 耗电；第一阶段不把能耗作为核心结论。[指标说明](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics) |

优先使用一台现有 Android 12+ 真机开始；第二台不同性能档位设备用于检验外部有效性，而不是购买前提。模拟器只做功能、脚本与采集流程验证，不能把它的性能数值代表真实手机。[官方测试教程](https://developer.android.com/codelabs/android-macrobenchmark-inspect)

普通 Windows 开发机足以支持应用级开发与 ADB 测量。可控网络可通过独立测试代理或 Linux 测试机/虚拟机实现；这是实验基础设施，不是新增产品服务。需要平台复现时再考虑 Linux AOSP 构建环境和可解锁的专用设备。

## 8. 推进顺序与停止条件

### 阶段 A：先证明“可以可信地测量”

阅读渲染时序和 Macrobenchmark 文档；建立固定图文浏览场景；保存原始 trace 和场景元数据。完成同一变体的重复测量，检查缓存、温度和脚本抖动。

退出条件：能解释指标起止点、能重跑、能识别缺失/损坏数据。此时不要求性能提升。

### 阶段 B：先归因，再决定题目

对照当前实现、按需加载和修正后的固定预取策略。对网络、解码、请求队列等分别进行受控干预。

退出条件：至少找到一个稳定瓶颈并有干预证据。如果预取不在关键路径上，应改为实际瓶颈研究，或停止投入复杂策略。

### 阶段 C：只实现一个机制假设

围绕已证实问题做最小调度/预算原型，保持界面、素材和其他参数不变。独立报告正确性、性能与额外开销。

退出条件：有合理基线、消融和退化场景；负结果也是有效产出。

### 阶段 D：选择是否进入平台研究

只有在设备、权限、时间和指导条件明确后，才选择 DroidPerf 或 Fleet 等 artifact。先在其原始目标环境验证，再考虑移植；不同时开始改 ART、内核和图形栈。

建议为首次可行性验证设置约一周的个人工作上限，产出“环境能否跑通、能否看到稳定现象”的结论。后续时间依据实验而定，不预先承诺性能提升比例或论文产出。

### 开始前需要确认的信息

- 真机型号、Android 版本、RAM、支持及实际使用的刷新率。
- 是否有独立可解锁/root 设备；默认没有，也不要求对主力手机操作。
- 可持续投入的时间、是否有系统方向导师指导。
- 是否能接触第二台设备，以及是否能固定网络与素材。

## 9. 建议阅读顺序

1. FrameTimeline 与 Macrobenchmark：先建立正确的测量概念。
2. Glide 缓存与预加载文档：核实实际依赖的语义，避免把错误使用当研究问题。
3. IMP、NAPPA：理解收益、成本与预测；选一个明确范围的方法复现。
4. Hubble：学习为什么性能研究必须评价观测开销，以及异常前信息的重要性。
5. DroidPerf：从“内存多少”进入“哪些对象、什么访问方式导致低效”。
6. Fleet 与 Silk：作为进阶阅读，理解对象级语义与页级管理之间的差距。
7. XTrace 与 MobiRL：观察近期工业实践和平台控制方向，不要求同时实现。

每篇阅读笔记只需回答：问题是什么、关键机制是什么、依赖哪些条件、与什么比较、哪些结果不能推广、在本项目中准备验证哪一小部分。详细执行口径见[端侧性能实验方案](端侧性能实验方案.md)。
