# 预加载技术复盘与汇报展开

2026-11-11。依据工作区 `2d2f8da` 的实际代码及 Glide 官方资料。本文区分设计意图、现有实现与待验证效果；没有运行性能实验或修改业务代码。

## 1. 预加载解决什么问题

双列瀑布流中的图片需要经过资源请求、下载或磁盘读取、解码/变换和显示。等卡片进入可视区才开始这些工作，用户容易先看到占位图。

预加载利用当前位置、滚动方向及点击行为，提前准备可能马上使用的资源。它把一部分等待移到用户到达之前，同时付出额外流量、内存和解码成本。

概念上，需要让“用户到达目标条目的剩余时间”尽可能覆盖“资源剩余准备时间”。当前实现采用固定窗口和间隔的启发式规则，没有根据网速和滚动速度动态计算最优窗口。

## 2. 三种工作分别负责什么

| 工作 | 对象 | 作用 |
| --- | --- | --- |
| 提前分页 | 下一页作品数据和媒体地址 | 取得后续内容 |
| 媒体预加载 | 已知地址的图片或视频帧 | 提前准备图片资源 |
| 页面状态恢复 | 已有列表、游标和滚动位置 | 返回后继续浏览 |

分页成功不代表图片已准备好，页面恢复也不等于提前下载了资源。

## 3. 实际触发规则

| 时机 | 当前行为 | 设计动机 |
| --- | --- | --- |
| 每页 Feed 返回 | 整批去重条目送入 LOW 预加载 | 预热已知资源 |
| 向下滚动 | 最后可见条目之后最多 3 项，LOW | 准备接下来可能看到的内容 |
| 向上滚动 | 最先可见条目之前最多 3 项，LOW | 支持回看 |
| 停止滚动 | 可视条目送入 MEDIUM | 准备当前关注内容 |
| 点击详情 | 该作品送入 HIGH | 为详情提供独立调度入口 |

双列瀑布流每列首末可见位置不同。向下使用所有列末位置的最大值，向上使用首位置的最小值。3 项是适配器条目数，不是 3 行或 3 屏。

滚动触发条件是距上次触发超过 500ms，且单次 dy 大于 10 或小于 -10。虽然变量名叫 DEBOUNCE，语义其实是**节流**：限制触发频率，而非等待停止滚动 500ms。dy 也是位移，不是归一化速度。

向下接近列表末尾约 5 项时，独立触发下一页请求，同时检查加载中、hasMore、分页暂停等状态。

两个需要修正的口径：

- **不是整个系统只预加载三张。** 整页返回已安排整批 LOW 工作，相邻三项仅限制方向触发的一次调用。
- **详情预取不是点击前预测。** Adapter 先启动详情，再调用预取；它选取首张图片或视频来源，并未加载作品全部媒体或详情业务接口。

## 4. 调度与尺寸设计

执行链为：HomeFragment/MainActivity 选择条目，PreloadManager 提交批次任务，逐项检查记录，再提交单项任务，通过 Glide.submit(width,height).get() 在后台等待完成，最后写入预加载记录。

LOW 与 MEDIUM 共用 normalExecutor，HIGH 使用另一个 executor。每池有容量 100 的 FIFO 队列，饱和时丢弃最旧排队任务。批大小 LOW/MEDIUM/HIGH 分别为最多 10/5/3。

设计意图是区分紧迫性，但不能把它称为严格优先级调度：MEDIUM 不会在 LOW 前插队，HIGH 不会抢占运行中的 LOW，代码也没有设置 Glide Priority.HIGH。批大小不等于图片并发数，外层批任务还会向同一池提交内层任务。

设预加载计算的卡片宽度为 W：

| 等级 | 图片目标宽度 | 视频帧目标宽高 | 记账期限 |
| --- | --- | --- | --- |
| LOW | max(60, W/8) | max(40, W/8) 的正方形 | 1 分钟 |
| MEDIUM | max(120, W/2) | max(80, W/4) 的正方形 | 3 分钟 |
| HIGH | W | W/2 的正方形 | 6 分钟 |

图片高度根据作品比例计算，最终宽高分别限制到 1024。设计体现“越可能被使用，准备尺寸越大”。但界面没有将这三档串成低清到高清替换链，不能称为已经实现渐进渲染。

缩小目标解码尺寸，不会自动缩小同一 URL 的网络文件。视频路径使用 asBitmap().load(videoUrl) 提取帧，不是独立 poster 图片或播放器分段预缓冲，不能保证只下载一张小封面。

## 5. 记账缓存与 Glide 缓存不同

PreloadManager 的 LruCache 最多保存 500 条记录，包括 URL、等级、尺寸、完成时间和媒体类型，不保存 500 张 Bitmap。键为 URL + priority；1/3/6 分钟是记录期限，不是图片缓存 TTL。每 5 分钟清理一次，调用时也检查记录期限。

Glide 才管理实际资源：活动资源、内存、解码变换后的磁盘资源及原始数据。复用已解码图片还要求尺寸、变换、类型等参数匹配，不仅是 URL 相同。[官方缓存说明](https://bumptech.github.io/glide/doc/caching.html)

因此，“最近预加载成功”不代表对应图片此刻仍在内存。图片使用 ALL 磁盘策略，视频分支使用 DATA；原始数据复用仍可能减少网络等待。

## 6. 关键偏差：预加载和实际展示请求不一致

| 项目 | 预加载 | 卡片展示 |
| --- | --- | --- |
| 尺寸 | 随 LOW/MEDIUM/HIGH 改变 | 卡片实际目标宽高 |
| 裁剪 | 未配置 centerCrop | centerCrop |
| 卡片宽度公式 | (屏宽 - 12dp) / 2 | 屏宽 / 2 - 8dp |

详情显示按屏幕尺寸请求，HIGH 仍然是卡片级尺寸。即使预加载成功，实际显示可能仍需重新解码和变换，只复用原始数据。Glide 的预加载指南也要求对齐预取与 Adapter 请求规格。[官方 RecyclerView 指引](https://bumptech.github.io/glide/int/recyclerview.html)

接下来应明确选择目标：

- **只提前下载**：采用数据预热策略，避免生成不被使用的小尺寸解码资源。
- **准备可直接显示的图片**：复用统一的 URL、尺寸、变换和类型配置。
- **低清到高清展示**：显式设计缩略图显示和替换流程。

当前不能同时宣称已实现上述所有收益。

## 7. 资源生命周期与并发问题

以下来自静态分析，没有在设备上逐项复现。

| 问题 | 代码事实与影响 | 改进方向 |
| --- | --- | --- |
| Glide Target 未显式释放 | submit().get() 不保存 FutureTarget，没有 finally 清理；取消外层 Future 不能证明底层加载和资源都停止 | 保存实际 Target，成功、取消、失败均有清理规则 |
| OS 优先级语义用错 | Java 的 Thread.NORM_PRIORITY 值 4/5 传入 Android Process.setThreadPriority；Linux nice 越小越优先，所以 HIGH 的 5 并不高于 4 | 使用 Android 常量并明确后台调度目标 |
| 线程数不是最多四个 | core=CPU数，max=max(core,min(4,CPU数×2))，8 核时每池可为 8；Fragment 和 MainActivity 还分别创建管理器 | 明确管理器所有权与全局并发预算 |
| 同 URL 的优先级升级没有合并 | key 含 priority，不同级别是不同 key；升级比较无法在普通查键路径合并 LOW/HIGH | 按资源规格去重，紧迫性单独维护 |
| pendingTasks 清理竞态 | 旧任务 finally remove(key) 可能删除新任务记录；极快完成也可能早于提交方 put | 任务代次与句柄绑定，完成时条件删除 |
| 反向/离页不会更新整个窗口 | 当前主要增量追加；onStop 取消 Feed 请求，管理器到 onDestroy 才 release | 维护当前需要的任务集合，撤销不再相关任务 |
| 部分内存回调只清记账 | RUNNING_LOW 缩减记录；optimizeCache 为空；部分严重回调调用 clearMemory | 按真实资源与 Target 处理压力，而不只删记录 |
| 队列淘汰无业务清理 | DiscardOldestPolicy 丢队首 Runnable，没有统一的任务淘汰状态通知 | 将调度、句柄和状态生命周期统一 |

Glide 官方明确提供 clear Target 释放请求资源；4.16.0 RequestFutureTarget 示例在 finally 中取消实际 Target。[Targets 文档](https://bumptech.github.io/glide/doc/targets.html)、[对应版本源码](https://raw.githubusercontent.com/bumptech/glide/v4.16.0/library/src/main/java/com/bumptech/glide/request/RequestFutureTarget.java)

Android Process 的调度优先级采用 Linux nice 语义，不能直接套用 Java Thread 优先级常量。[Android API 文档](https://developer.android.com/reference/android/os/Process#setThreadPriority(int))

## 8. 建议的复盘顺序

1. 先闭合 Target 清理、任务取消和代次校验，保证资源生命周期正确。
2. 统一预取与显示的请求规格，明确要提前完成下载还是解码。
3. 评估是否保留整页预热，建立全局并发预算、同请求复用和窗口淘汰。
4. 再测量效果，之后才讨论动态窗口、弱网策略或更复杂预测。

不宜先靠增加线程、扩大缓存或加大预取范围追求效果。

## 9. 怎样测量才有意义

同设备、同数据、同网络，对比开启/关闭预加载，并分冷缓存、热缓存。关注：

- 卡片进入可视区到图片可用的时间及占位图比例。
- Glide DataSource：MEMORY_CACHE、RESOURCE_DISK_CACHE、DATA_DISK_CACHE、REMOTE。
- 预加载完成后实际使用的比例、未浏览内容消耗的流量。
- 持续/反向滚动的帧耗时、峰值内存、并发数。
- 离页、详情返回、切栏目后未结束任务和资源是否符合规则。

代码搜索未发现直接引用 PreloadManager 的专项测试；这不能证明所有间接测试都不存在。本次没有执行这些测量。

## 10. PPT 可以用两页讲

**第一页：用户接下来会看什么。** 双列列表标出可视区、方向窗口和分页边界，解释方向选择、500ms 节流以及分页与媒体预取的区别。整页返回也会预热，不能说总共只加载三项。

**第二页：提前准备的资源如何被复用。** 展示条目选择、调度、Glide 缓存、实际显示链路，解释数据预热和最终资源复用的差异。未完成的请求规格统一和资源清理作为后续完善点，不包装成已经验证的成果。

可用口径：围绕连续浏览，我们实现了提前分页、按方向预取媒体和页面状态保留。当前采用固定窗口及节流，并由 Glide 管理资源；进一步复盘发现，请求规格和生命周期仍需完善，实际收益需要设备测量验证。
