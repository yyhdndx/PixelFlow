## 发现：[P2] 同版本迁移变化无法识别，旧 JAR 仍可被判为与源码一致

位置：`intelligence/scripts/verify_profile_pipeline.py:269–270`，以及上游
`jar_migrations` / `source_migrations` 的迁移清单读取逻辑。

当前清单只保存 `{版本号: 文件名}`，比较时又仅比较字典键的集合，没有核对文件名和 SQL 内容。
若构建 JAR 后修改同一个版本的 SQL，或者把 `V9__post_creation_idempotency.sql` 改名为
`V9__different_migration.sql` 而继续使用旧 JAR，两个集合仍然都是 `{9}`，返回
`ok=true`、`source_checked=true`。本次独立探针分别复现了这两种误报。

Flyway 校验不能补上这个缺口：链路脚本创建的是全新测试库，由旧 JAR 中的迁移初始化，
Flyway 校验的也是该 JAR，而不是当前源码。因此正常链路测试通过不代表当前检出的 SQL 已被验证。
这不满足任务 14 对“旧 JAR 与新源码不一致不能得出成功结论”的要求。

建议读取并比较每个迁移的文件名及内容摘要，保留版本集合检查和 Flyway 自身校验；摘要报告只需
列出不一致的版本或文件名，不输出 SQL 正文。补充“同版本改名”“同名 SQL 内容变化”的失败回归，
确认错误时主程序退出非零，CI 停止后续打包。

复现脚本及输出保存在本机：

- `D:/desk/software_engineering/review-runtime-20261028/reproduce_migration_mismatch.py`
- `D:/desk/software_engineering/review-runtime-20261028/reproduce_migration_mismatch.json`

探针只创建临时 JAR 和临时源码目录，不修改被审代码或数据库。它针对“应当拒绝不一致”的断言退出 1；
这是独立 review 发现的失败，不计入提交者原有测试的通过数。
