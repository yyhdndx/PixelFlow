## 需整改的问题

### [P2] 数据库清理未记录本次创建的所有权，会删除原先存在的同名库

位置：`intelligence/scripts/verify_profile_pipeline.py:146–156,326,718–720`。

`create_databases()` 使用 `CREATE DATABASE IF NOT EXISTS`，而 `created` 在创建前就包含全部计划名称。若随机后缀与保留的历史测试库重名，脚本继续使用既有库；运行成功或启动失败后，`finally` 都会删除列表中的库。名称前缀校验只限制命名，不能证明库是本轮创建的。

在本轮独立 MySQL 8.4 实例内预建一个带哨兵表的测试库，固定随机后缀模拟重名，再让 Java 启动阶段报错。结果：脚本返回失败，同时删除了运行前已存在的库和哨兵表。复现只操作验收自建实例中的样例数据，没有访问开发库或云端。

整改：创建时拒绝已有库或更换名称；仅在每个 CREATE 确实成功后登记所有权；清理仅遍历成功新建的库。补重名、第二个库创建失败和服务启动失败的回归。仅增加随机串长度不能替代所有权记录。

### [P2] 断言明细绕过账号脱敏，报告仍包含完整账号 ID

位置：同文件 `Evidence.equality():73–74`、当前画像比较 `392–393` 及历史响应明细。

顶层 `accounts` 已截断标识，但 `checks[].detail` 直接记录比较对象的完整 `repr` / JSON。实际成功报告仍出现完整 `user_id`；三个检查明细含该字段。因此“报告只保留脱敏账号”的承诺并未覆盖整个产物。

整改：写入/打印报告前统一脱敏，或仅保存相等结果、字段名、版本和数量，不保存完整画像对象。新增检查应扫描整个 summary 和打印输出，不能只检查顶层 `accounts`。本轮证据摘要未复制完整账号标识。

### [P3] 开始时间使用单调时钟转换，生成错误的 1970 年日期

位置：同文件 `328`、`677`。

`started = time.monotonic()` 适合计算耗时，不能传给 `time.localtime()`。本轮于 2026-10-25 执行，产物却记录 `started_at=1970-01-03T05:17:22`。应分别记录墙上时钟和单调时钟，前者用于审计日期，后者用于耗时。
