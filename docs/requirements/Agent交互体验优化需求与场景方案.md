## 1. 要解决什么问题

用户使用 AI 时，通常仍有阅读原文、浏览搜索结果、编辑作品和处理评论的需求。AI 生成较慢不应使这些操作一起等待。

| 编号 | 问题 | 用户感受到的影响 | 解决方向 |
|---|---|---|---|
| P01 | AI 与普通业务请求共用串行执行队列 | AI 正在生成时，新发起的列表、点赞等请求可能排队等待 | 分开调度普通请求与 AI 请求，限制 AI 并发 |
| P02 | 完整生成后才一次性显示 | 长时间只有加载提示，不知道是否仍在工作 | 真实阶段提示；适合的场景逐步显示内容 |
| P03 | 请求和结果依附具体页面 | 离开、返回或页面重建后，可能取消任务、丢结果或重复生成 | 在页面之外管理任务状态；返回时恢复已有结果 |
| P04 | 等待界面遮挡主要内容 | 想一边等总结一边读原文，却被弹窗挡住 | 使用可收起的区域，避免阻挡阅读的加载弹窗 |
| P05 | 生成结果可能与用户后续操作冲突 | 新编辑被旧文案覆盖，旧问题的答案出现在新搜索中 | 按账号、请求、作品或草稿版本隔离；结果主动采纳 |
| P06 | 部分生成内容与完成结果缺少区别 | 网络中断后误以为回答完整，或保存不完整内容 | 明确区分生成中、完成、中断、取消与失败 |

本次目标是改善等待过程和并行操作体验，不承诺模型总生成时间必然缩短。

## 4. 各场景的具体要求

### 4.1 智能搜索与多帖综合回答

**用户故事：** 用户搜索“适合新手的拍摄技巧”，先浏览普通搜索结果，在 AI 整理答案时打开其中一篇作品，再返回阅读综合回答。

- 普通列表与 AI 回答独立加载，任何一方失败不清空另一方的结果。
- AI 区域展示真实阶段，例如“正在查找相关作品”“正在整理回答”；无法获知进度时不显示虚构百分比。
- 检索和来源权限校验完成后，显示可跳转的来源列表，逐步补充回答正文。
- 用户进入详情再返回时，恢复当前问题的进度与已生成文字，不自动重新请求。
- 用户修改并提交新问题时，取消仍在生成的旧问题；旧请求的迟到结果不得覆盖新问题。
- 已完成的回答可在本次 App 使用期间保留。首版不增加跨启动搜索历史。
- 无结果时明确显示“社区内暂未找到相关作品”，不为制造流式效果调用模型编造内容。
- 引用编号与来源对应；只使用当前账号可见的已发布作品。来源失效或校验失败时，不再将回答展示为可用的完整结果。

**验收：** AI 尚未完成时能打开普通结果、点赞或查看评论；返回仍能看到原问题的生成进度；新问题不会收到旧回答；无结果、断网和来源无权访问均有明确状态。

### 4.2 AI 辅助文案生成

**用户故事：** 作者让 AI 帮忙写文案，同时继续选图、修改标题和正文。

- 保留编辑区可操作；AI 在独立建议区域生成，不锁住整页。
- 请求保存发起时的输入快照，并绑定账号、草稿和输入版本。
- 用户继续修改后，旧输入生成的建议仍可查看，但标明“基于之前的内容生成”。
- 结果不自动覆盖正文。用户选择“插入”或“替换”后才修改草稿，替换应允许撤销。
- 生成期间可以预览文字；只有完整且通过校验的候选才能一键采用。
- 同一草稿同一输入的连续点击不重复请求；重新生成应显式取消或替换原任务。
- 离开编辑页但保留草稿时，在 App 内继续任务；删除或明确放弃草稿时取消任务。

**验收：** 生成期间修改正文，结果到达后用户输入不变；返回同一草稿可看到建议；候选不会串入其他草稿；不完整结果不能一键覆盖正文。

### 4.3 长文本作品总结

**用户故事：** 用户点击总结后继续阅读原文，准备好后再展开查看要点。

- 用作品内可展开、收起的总结区域承载结果，替代遮挡阅读的等待弹窗。
- 收起区域不取消任务；重新展开恢复已有内容。
- 概括和要点按完整内容块显示，避免半条要点被当成正式结果。
- 按账号、作品及内容版本保存状态；原文改变后旧总结应失效或明确标记。
- 切换作品时不自动为每篇长文生成总结，也不把上一作品的总结带入下一作品。
- 短文继续遵循现有无需总结的处理；失败提示可以继续阅读原文。

**验收：** 总结中仍可滚动原文、看评论；关闭总结区域再打开不重复生成；切换作品不串内容；原文变化不会静默复用旧总结。

### 4.4 自动回复规则提炼

**用户故事：** 作者输入“有人问拍摄地点时告诉他在玄武湖”，让 AI 整理规则，同时查看已有配置。

- 以“建议规则”展示生成结果，每条包含完整场景和答案。
- 建议通过格式与长度等校验后，逐条出现；不直接展示尚未闭合的 JSON 或半条规则。
- 作者可以编辑、勾选与保存；生成完成不等于已经启用自动回复。
- 输入描述变化后，已有建议标明来自旧描述；旧请求不得覆盖新请求结果。
- 重试或重复点击保存，不得无意创建重复规则。

**验收：** 等待期间仍能看已有规则；未确认的建议不生效；失败不修改原配置；保存的是作者选择确认的完整规则。

### 4.5 评论自动回复判定

**用户故事：** 用户发布评论后继续看作品，作者配置的自动回复稍后出现。

- 评论发布成功应以评论保存成功为准，不依赖模型判定是否完成。
- 模型只匹配场景，回复正文继续取作者配置，不改成自由生成回复。
- 无匹配或模型失败时不自动回复，不因此撤销或报错已成功的评论。
- 同一评论不能因重试产生多次相同自动回复；评论删除、作品不可见或规则被停用后，应重新确认是否仍允许回复。
- 客户端通过后续刷新或既有通知能力获取回复；不要求为这条回复建立文字流。

**验收：** 人为延迟模型时，评论仍能正常提交；故障不影响评论浏览；重复执行不会重复回复。

此场景涉及服务端任务可靠性，需单独核对现有执行方式。若要求服务重启后仍能继续处理，需要持久化任务及重试机制；不能把内存后台线程当作可靠任务系统。

### 4.6 智能审核与管理员建议

**用户故事：** 作者提交作品后继续浏览；管理员请求审核建议后，可以先查看其他待审作品。

- 提交、待审核、审核结果分别表达；提交成功不等于审核通过。
- 等待审核期间允许正常浏览，但不能绕过作品可见性规则提前进入公共信息流。
- 管理员建议绑定作品版本；切换作品后，旧建议不能显示到新作品上。
- 风险级别、建议动作和理由作为完整结果校验后展示，避免半截理由被误认为最终结论。
- 模型失败显示建议暂不可用，沿用既有审核规则和人工处理路径，不自动视为通过。
- 不在本任务中修改“谁有权批准作品”等审核权限规则。

**验收：** 作者等待审核仍可浏览；管理员可以切换待审项；建议与作品版本一致；AI 故障不会直接放行作品。

### 4.7 智能推荐与画像

**用户故事：** 推荐更新较慢时，用户仍希望继续看当前已有作品。

- 保留当前可用列表，刷新失败不把已有内容全部清空。
- 没有推荐结果时使用约定的普通信息流降级；降级结果仍遵守权限与屏蔽规则。
- 画像更新与列表浏览分开，不要求用户等待画像计算结束。
- 更新后的推荐在明确刷新时应用，避免用户正在点击的卡片突然换位置。
- 缓存必须按账号和有效期隔离，不因为“优先显示旧数据”而展示其他账号的数据。

**验收：** 推荐服务慢或不可用时仍有可浏览内容；退出、切换账号不串数据；用户浏览期间列表不会无提示重排。

### 4.8 博主评论总结（预留）

**用户故事：** 博主希望了解某篇作品评论里的高频问题、反馈和争议，同时继续管理社区内容。

- 发起时明确作品和统计范围，如最近若干条评论或指定时间段。
- 展示总体概括、高频主题和代表性评论入口；可以分块生成。
- 标明覆盖范围和生成时间，新评论产生后不伪装成已纳入总结。
- 支持回到该作品查看结果；失败不影响评论管理。
- 该功能尚需独立需求和接口任务，不作为本次已有功能优化的完成项。

## 5. 所有场景共用的交互规则

### 5.1 请求调度

- 普通业务请求与耗时 AI 请求使用独立执行资源，不让 AI 占住唯一的请求执行位置。
- AI 任务采用有限并发与有限等待队列；满额时显示等待或稍后重试，不无限堆积请求。
- 首版并发额度在实施时根据服务能力设定并验证；应避免一个长任务占满所有 AI 容量。
- 按实际接口识别所有耗时 AI 请求，包括长文总结和规则生成，不能只处理搜索和文案。
- 保留点赞、保存等写操作必要的顺序保障；并发后仍需统一处理登录刷新、账号切换和迟到响应。
- 拆分客户端队列不能解决服务端资源争用，仍需有服务端超时与并发限制。

### 5.2 页面、账号与任务生命周期

首版保证 **App 保持运行期间的页面切换与页面重建恢复**。不保证 App 进程被关闭后仍能完成，也不承诺锁屏或长期后台运行时连接持续有效。

| 用户动作 | 约定行为 |
|---|---|
| 打开作品详情，再返回搜索页 | 原搜索任务继续，恢复进度和结果 |
| 收起总结或建议区域 | 任务继续，不重新发起 |
| 提交新搜索、点击重新生成 | 替换对应旧任务，忽略旧响应 |
| 明确停止生成 | 取消请求；已有片段标为未完成 |
| 删除或放弃草稿 | 取消该草稿相关任务 |
| 退出或切换账号 | 取消旧账号任务，清理结果与 UI 状态 |
| App 进程被关闭后重新打开 | 不假装任务仍在运行；允许用户重新发起 |
| 网络断开 | 显示中断；用户主动重试，不无限自动重复调用模型 |

任务与结果需设置数量、大小和保留期限上限；首版使用期间的结果保留不等于新增永久历史记录。

### 5.3 展示状态与操作

统一区分：等待执行、检索或准备中、生成中、已完成、已取消、失败或中断。无结果是有效业务结果，应与服务故障区分。

- 只有收到完成标记且校验通过，才将结果标为“已完成”。
- 中断后的部分内容明确标记“内容未完成”，不作为完整候选一键采用，也不写为成功的会话结果。
- 新内容追加时，用户若已向上阅读，不强制滚动到底部。
- UI 合并短时间内的文本片段更新，避免每个字符都触发整页刷新。
- 结果就绪优先在所属区域提示，不为每次生成完成弹出全屏提示或系统通知。

## 6. 流式显示如何落地

DeepSeek 的 Chat Completions 接口支持 `stream: true`，通过 SSE 返回增量内容，调用外部接口即可实现，无需自行部署模型。[官方接口说明](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)

需要整条链路支持：模型输出片段 → Python 解析与发送 → Java 鉴权、校验与转发 → 网关及时传输 → Android 增量展示。仅修改模型参数，或完整获取后播放打字动画，都不能达到本需求。

实施前先补充契约，至少定义阶段、来源、文本增量、完整内容块、完成和错误事件；字段名称以最终契约为准。保留现有完整响应接口，供兼容与降级使用。

- 搜索来源先验证再输出，最终答案仍需检查引用与完整性；不能为提前显示绕过现有权限边界。
- 结构化结果需要增量解析或调整生成协议，不能把原始 JSON 直接展示。完整内容块的发布也必须经过相应校验。
- 流开始前失败可使用正常 HTTP 错误响应；流开始后失败使用错误事件，连接意外断开也按未完成处理。不能在已输出正文后再承诺改为 HTTP 502。
- 完成时保留会话、来源、降级状态与轨迹标识；中断任务应可核查，且不能将其部分答案登记成完整成功结果。
- 超时、代理缓冲和断开连接的资源释放要端到端验证。客户端取消后应尽力停止后续处理，但不承诺上游模型一定立即停止计费。

## 7. 是否需要消息队列

| 要解决的需求 | 首选方式 | 是否必须引入消息队列 |
|---|---|---|
| AI 请求不挡住普通请求 | 客户端分开调度，服务端限制并发 | 否 |
| 已生成的文字尽早显示 | 端到端流式传输 | 否 |
| App 内换页后继续查看 | 页面之外管理任务与状态 | 否 |
| App 关闭后继续生成，回来可查 | 服务端持久化任务、结果查询与恢复 | 需要持久化机制；具体是否使用队列另行设计 |
| 审核、自动回复在服务重启后可靠恢复 | 持久化任务、去重、重试与失败处理 | 适合评估消息队列，但队列本身不等于完整可靠性方案 |

首版不为文字流式显示单独引入消息队列或新增任务中心。后台可靠处理作为独立范围评估。

## 8. 实施分工与顺序

| 批次 | 交付内容 | 主要负责侧 | 前置依赖 |
|---|---|---|---|
| A | 普通与 AI 请求隔离、取消和账号隔离、任务状态基础能力 | Android；Java/Python 配合确认接口耗时与限制 | 覆盖现有全部 AI 入口 |
| B | 智能搜索流式试点，普通结果独立可用，进入原文后返回恢复 | Android + Java + Python；部署配置配合 | 先完成流式契约；保留原完整接口 |
| C | 长文总结可收起、文案主动采纳、规则建议按块显示 | Android 为主；Java/Python 支持增量结果 | 复用 A/B 的任务和传输能力 |
| D | 审核、自动回复的后台可靠处理与推荐刷新优化 | Java + Python；对应客户端配合 | 分别审查现状，另开具体任务 |
| E | 博主评论总结 | 三端按新需求协作 | 明确评论范围、权限与来源契约 |

每批独立验收，不以所有场景完成流式改造作为前一批上线的前提。后续代码分支从届时最新 `dev` 创建。

## 9. 联调与验收清单

以下为待执行标准，本文不宣称已经通过。

- [ ] 将 AI 响应人为延迟 30 秒，期间普通请求在 AI 完成前即可发出并正常返回，不等待这 30 秒结束。
- [ ] 验证搜索、文案、长文总结、规则生成均进入正确的请求调度路径。
- [ ] 可控流测试先发送一个片段、延迟 5 秒再结束，手机在结束前展示首段；真模型联调同样观察到首段早于完整结束。
- [ ] 经实际部署网关验证仍能逐步到达，排除代理攒完整响应的情况。
- [ ] 搜索打开原文再返回、页面重建、总结收起再展开，不重复发起同一有效任务。
- [ ] 新旧问题、不同作品、不同草稿、不同账号之间不串结果。
- [ ] 生成文案期间继续编辑，结果到达后不覆盖用户新输入。
- [ ] 完成、中断、主动取消、超时和零结果分别显示正确状态；部分结果不被判为成功。
- [ ] 搜索的未登录拒绝、来源可见性、引用对应和轨迹可查要求保持有效。
- [ ] 队列满、连续点击、多个任务并行时不无限增加请求；普通写操作保持正确顺序。
- [ ] 记录普通请求排队时间、AI 首段展示时间、总耗时和重复请求次数，用于比较改造前后效果。
- [ ] 原有完整响应接口与非 AI 搜索仍能工作，AI 故障不清空普通搜索结果。
