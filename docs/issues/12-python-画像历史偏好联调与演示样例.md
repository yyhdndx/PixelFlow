## 问题与目标

当前已有事件同步、画像重算、历史快照、可恢复调度和三个规则 Skill。Java 也已提供当前/历史画像代理。Android 历史与偏好页面已写出，但页面恢复测试使用的是 MockWebServer，尚不能证明真实 Java → Python → 分析库链路可演示。

本任务验证既有能力并补齐联调缺口，交付两账号、可重复运行的样例与证据。不要重新实现历史接口、周期调度器或偏好存储，也不要把固定 Skill 流水线称为 Agent。

## 需要走通的链路

1. 在隔离本地 Java/Python/MySQL 环境准备两名普通用户和少量已发布测试作品，通过真实业务接口产生可区分的点击、停留和服务端点赞事件。记录生成的 ID 和相对时间，避免依赖共享数据库固定 ID。
2. 运行现有 `scheduled_maintenance` 包装器执行一轮有界维护，确认同步及重算结果；观察服务端持久化游标和历史版本。脚本读取已有真实事件，不直接写入画像表制造“同步成功”。
3. 用两账号各自的 JWT 通过 Java `/api/users/me/profile` 和 `/api/users/me/profile/history` 读取结果；与 Python 本人接口对照。演示 App 的访问入口始终为 Java，不把 Python 端口开放给手机。
4. 通过 Java 修改个性化开关、主题抑制、作者屏蔽及作品排除，验证 Python 推荐预览读取的权威偏好、版本与过滤效果；历史画像仍保留生成时的快照。

当前普通 `/feed/` 不会因为偏好设置自动变为个性化 Feed。主题抑制只移除对应个性化权重，不表示所有该主题作品必须被排除；个性化关闭不等于删除画像或停止事件采集。验收断言必须遵守现有契约。

## 验收标准

- [ ] 两账号的数据和历史严格隔离；伪造查询参数不能切换身份；失效/停用会话按契约拒绝。
- [ ] 新用户当前画像为 version=0 冷启动、历史为空；读取历史本身不生成版本，不推进同步游标。
- [ ] 同步一批有效事件后版本与可解释的主题分数按规则更新；重复同步同一批及空同步不重复计分，游标可恢复。

- [ ] 单独读取历史、修改偏好不改写已有历史快照；关闭个性化、主题抑制、作品排除、作者屏蔽符合上述语义。推荐执行期间偏好版本变化时，不交付过期结果。
