# [Python] 为事件同步和画像重算提供可恢复的周期调度

状态：待发布的 Gitee Issue 草稿；`04` 是本地任务顺序，不是线上编号。优先级 P1，建议 Python 同学负责。可与 Java 任务 01、02、03 并行，不依赖它们的接口或数据库变更。

## 用户价值与当前实现

用户持续浏览、点赞后，希望画像能在后台更新，而不是每次依赖开发者手动同步。两端服务常驻并不意味着分析任务会定时执行。

现有 [maintenance.py](../../intelligence/src/pixelflow_intelligence/maintenance.py) 已实现单次有界维护：调用 Python 内部同步/重算接口，输出 JSON，完成/未完成/失败分别退出 0/2/1。已有时间预算、页数上限和 `--refresh-after`，不能重复实现另一套业务计算。

已部署的 MySQL 分析库保存事件 checkpoint，事件同步可以从数据库进度恢复。但 CLI 的画像扫描游标需要调用方保存；每次从空游标开始，在用户超过单轮分页容量时可能反复扫描前段用户。云端目前没有启用周期分析定时器。历史 CentOS 文档中的 timer 片段仅作参考，不算已部署。

## 任务交付

1. 新建独立 `pixelflow_intelligence.scheduled_maintenance` 入口，复用现有 maintenance.run、配置校验与 HTTP 客户端约束，负责调度状态、互斥和退出码；保留现有手动 CLI 的行为。
2. 在 `deploy/systemd/` 新增 `pixelflow-analysis.service` 和 `pixelflow-analysis.timer` 模板，服务使用现有虚拟环境、pixelflow 用户与本机 Python 地址。
3. 在 `deploy/分析调度使用说明.md` 说明安装、首次手动运行、启停、检查日志、失败重试、状态文件备份与恢复。本任务只交付代码和模板，**不直接登录、修改或启用共享服务器任务**，由部署负责人验收后发布。

## 运行约定

- 默认启动后约 2 分钟触发首次执行，上次任务结束后约 5 分钟再次执行；这些是调度间隔，不承诺精确的端到端画像时效。
- 采用 oneshot service，执行本地 `http://127.0.0.1:8001` 的内部维护接口；不新开公网接口，不直接访问 Java MySQL。
- 继续使用 PIXELFLOW_MAINTENANCE_URL 与 PIXELFLOW_INTELLIGENCE_TOKEN。root 私有 EnvironmentFile 由 systemd 注入；禁止在 ExecStart、命令参数、日志或状态文件写入 token。
- 单轮默认预算 120 秒，service 的总超时略大于此预算。退出 0 表示该轮完成，2 表示达预算/页数限制仍有待处理内容，1 表示失败。timer 下次照常触发，不设置无间隔的失败重启循环。
- 显式区分 incomplete 与 complete：即使使用 SuccessExitStatus=2 避免把分页截断算成服务故障，JSON 日志仍必须显示 incomplete，不能伪装成已追平。

## 状态与并发要求

默认状态目录 `/var/lib/pixelflow/python/maintenance`，可用独立配置项调整；服务仅允许在此必要目录写入，文件由 pixelflow 私有持有。

调度状态只记录画像扫描的 refresh_after、上次执行时间/结果等非敏感进度，不复制事件 checkpoint、不保存用户明细。事件同步继续以 MySQL checkpoint 为唯一来源。

- 同步/刷新未完成时保留可安全续跑的扫描游标；完成全轮扫描后将 refresh_after 重置为空，使下一轮从头检查画像过期状态。
- 成功响应的游标才可持久化；异常、超时、进程中断不得跳过未确认页面。允许安全重放，依赖已有重算幂等性。
- 状态文件使用临时文件和原子替换，避免半写入。损坏状态应显式报错并说明恢复办法，不静默清空或宣称成功。
- 在入口层持有进程锁，防止同一个状态目录下 timer 与手动包装器同时运行。锁忙时给出可识别结果；退出/崩溃后锁可释放。
- 现有直接运行 maintenance CLI 的运维方式不会自动受新锁约束，应在文档说明生产手动触发统一使用新包装器。数据库已有行锁继续负责业务事务一致性。
- 需要定义状态文件的版本及格式；保留对用户删除/新增导致扫描集合变化的合理处理。新用户落在旧游标之前时，完整扫描结束后的下一轮可以覆盖，不承诺单轮快照。

## 并行开发边界

- 主要改动：新包装器、新 `tests/test_scheduled_maintenance.py`、新增 systemd 模板和独立使用说明。
- 不改 Java、Android、users 表、Java OpenAPI，也不新增分析库表或修改 MySQL V1 schema。
- 默认通过现有 maintenance.run 的参数和返回值续跑，不改既有 HTTP 接口、画像算法、事件字段或 checkpoint 行锁逻辑。若确实发现现有 run 无法满足要求，先单独说明阻塞点，不能悄悄改变现有 CLI 契约。
- 不顺带引入 Celery、Redis、消息队列或新的模型依赖。本期单机 systemd 足够。
- 公共 README 的入口由合并时统一补充，不要求本任务同时重写上手指南和部署历史。

## 验收条件

- [ ] 连续两轮能够自动同步新行为并触发画像重算，不需要手工调用 HTTP 接口。
- [ ] 完整扫描后游标归零；超过单轮页数限制时，下轮继续后续用户，不永远停在第一页。
- [ ] 覆盖空数据、同步积压、刷新分页上限、时间预算耗尽、401/503、网络超时和异常响应，结果与退出码明确。
- [ ] 覆盖进程重启、状态损坏、原子写失败、同目录并发运行；没有游标跳跃或密钥泄漏。
- [ ] 已确认页面可重放，失败页不被当成完成；事件 MySQL checkpoint 始终由现有同步事务维护。
- [ ] `systemd-analyze verify` 检查模板通过；在独立 Linux 测试环境实际验证首次触发、周期触发、停止、再次启动及服务超时，不用 Windows 单元测试代替 systemd 验收。
- [ ] Python 自动测试通过；使用独立 MySQL 测试库和本地 Java 验证一次真实同步/重算，结果能由 `/internal/status` 核对。
- [ ] 文档包含不展示令牌的手动触发、日志查看、停止 timer、状态恢复步骤；禁止测试连接共享业务数据库。
- [ ] PR 写明所有新增配置、文件权限、调度间隔与超时，并标注“模板已验证”和“云端已启用”是不同状态。

## 不在范围

云端自动启用、数据备份定时器、跨机器分布式调度、推荐算法或 Agent、画像删除、历史事件清理、实时推送及监控平台。当前 `/internal/status` 不代表绝对追平上游，本任务不把其 unknown backlog 改成未经测量的零。
