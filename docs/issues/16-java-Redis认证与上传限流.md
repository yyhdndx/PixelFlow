# 16：Java 接入 Redis，实现认证与上传限流

负责人：Java 同学。优先级：两周交付必做。预计工作量：2–3 天开发与测试，部署联调另计。

建议分支：`feature/java-redis-rate-limit`，从最新 `origin/master` 创建。

这是仓库内任务编号，尚未创建 Gitee 线上 Issue。与 [任务 15：推荐交付入口](15-java-推荐交付入口.md) 独立；同一负责人先完成在手任务，不要求同时维护两个未完成分支。

## 背景与目标

项目需要实际使用 Redis。当前 Java 使用 MySQL 保存账号、会话、作品和互动，尚未接入 Redis。本任务用 Redis 保存有过期时间的限流计数，减少短时间重复登录、批量注册与频繁上传；两个 Java 实例共享同一额度。

范围只包含认证与上传限流，不迁移会话、不做 Feed 缓存、不改推荐算法、不新增 Flyway 迁移。

## 接口与行为

以下是可配置的初始值，不是固定性能结论。测试使用较小阈值和短窗口。

| 接口 | 限流维度 | 初始额度 |
| --- | --- | --- |
| `POST /api/auth/login` | 客户端 IP 总量 + 同 IP/账号组合；两者均未超额才允许 | IP：100 次/60 秒；IP/账号：10 次/60 秒 |
| `POST /api/auth/register` | 客户端 IP | 10 次/600 秒 |
| `POST /api/media` | 已认证用户 ID | 30 次/60 秒 |

- 采用首次请求开始计时的固定窗口；请求到达即计数，不仅统计登录失败。成功登录不重置额度，超限请求不延长窗口。
- IP 总额度用于限制不断更换账号的请求；账号不存在也计数，不能通过限流响应判断账号存在与否。账号取值规则与现有认证一致，不另改大小写语义。
- 登录/注册应在执行密码校验、创建账号前判断；登录 IP 总量应覆盖无效请求体，避免依赖有效用户名才能计数。读取请求体不得破坏原有绑定/校验。
- 上传先完成认证，再在媒体持久化前判断。无身份请求保持 401，不接受客户端自报 userId；仍保留现有上传大小/类型限制。本任务不宣称能阻止所有上传网络流量或 multipart 临时文件开销。
- 超限返回 HTTP `429`，统一错误体使用 `ApiErrors.body`，`code=RATE_LIMITED`，包含可读 message 和真实 `requestId`；响应头包含 `Retry-After`（剩余窗口秒数向上取整，至少 1）及 `Cache-Control: no-store`。多个维度同时超额时给出足以等待这些窗口结束的重试时间。
- 被 429 拦截的请求不得执行注册/媒体业务写入。其他正常响应、鉴权和事务语义保持兼容。若在过滤器返回错误，显式复用错误体，不能依赖 ControllerAdvice 自动处理过滤器异常。
- `/health`、普通 Feed、画像查询、刷新令牌、退出不纳入本轮限流。

## Redis 与配置

- 使用 `spring-boot-starter-data-redis`，依赖版本交给现有 Spring Boot 管理，不顺带升级框架。
- 使用 Lua 原子完成计数、首次设置 TTL、返回计数及剩余 TTL；不得分开发送 INCR/EXPIRE 导致计数键永久存在。重复请求不得刷新 TTL；明确处理无 TTL 的异常计数键。
- 多维度可分别执行原子脚本：一次请求即使被其中一个维度拒绝，也属于已发生的尝试；写清计数规则。无需引入 Redis Cluster 或分布式锁。
- Key 包含环境/应用命名空间、规则版本、接口与身份摘要。IP/账号组合使用无歧义编码后摘要，不放密码、令牌、正文；摘要不是匿名化承诺，不在日志输出原始身份或完整 Key。
- 提供总开关、各规则额度/窗口、Redis 地址/认证/数据库与连接/命令超时配置。未开启时不得访问 Redis；上线必须显式启用并提供真实限流证据，不能仅以添加依赖验收。
- Redis 故障采用 **fail-open**：连接或命令失败时放行原有业务，记录脱敏且抑制重复刷屏的降级日志/计数；配置有限超时，无请求内无限重试，不返回伪造的 429。恢复后自动重新使用 Redis。注明故障期间限流保护减弱，不宣称始终精确限制。
- 配置错误（如额度≤0）应在启动校验时明确报错；Redis 暂时离线则不应阻止基础服务启动或登录/浏览可用。
- Redis 仅用于临时计数，实例重启后额度可能重置；不作为业务事实来源。

## 可信客户端 IP

- 当前部署由 Nginx 转发到本机 Java。仅在连接来源属于显式配置的可信代理时读取代理提供的客户端 IP，其余使用 socket 来源地址；不要直接信任请求任意提供的 `X-Forwarded-For`。
- 延用部署文档中 Nginx 覆盖 `X-Real-IP`/`X-Forwarded-For` 的单跳方式；选择一个来源并写清配置，合法性校验失败回退到 socket 地址。
- 检查容器自动处理 forwarded headers 的配置，避免可信来源判断前原始来源已被改写。测试覆盖直连伪造头、可信代理、无效头和不同客户端分桶；不要扩大为通用多级代理解析库。

## 自动化验收清单

- [ ] 正常登录、注册、上传保持原响应；未登录上传仍为 401。
- [ ] 配置同一维度 5 次/窗口，前 5 次进入业务，第 6 次 429；错误体、请求标识、Retry-After 正确；超限无业务副作用。
- [ ] TTL 到期恢复额度；连续超限不续期；没有永久计数键。
- [ ] 同 IP 不同账号的组合额度独立，但仍共享 IP 总额度；不同 IP 独立；不同用户上传额度独立。
- [ ] 多并发请求不会穿透额度。使用真实 Redis，不能仅用 mock 或进程内 Map 证明原子性。
- [ ] 两个 Java 应用实例共享同一 Redis 和规则命名空间，合计额度仍为 N；不是每实例各 N。
- [ ] 伪造代理头不能绕过限流；可信代理场景不会把所有用户错误地归为 Nginx 的 IP。
- [ ] Redis 连接失败/命令超时按有限时间降级，正常业务仍可执行，故障记录可查；恢复后重新限流；关闭开关时不连接 Redis。
- [ ] 隔离测试使用专属 Redis 实例或唯一 Key 前缀，仅清理自己创建的键，禁止在共享环境 FLUSHDB/FLUSHALL。
- [ ] CI 启动真实 Redis 服务，明确启用限流测试；Redis 缺失必须失败，不能静默跳过。保留既有 Java/MySQL、Python 与真实画像链路检查。
