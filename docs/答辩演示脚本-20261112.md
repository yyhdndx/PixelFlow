# PixelFlow 答辩演示脚本（数据闭环版）

## 一、演示目标

用一个真实用户的完整旅程，展示系统的**数据闭环**：

```
注册登录 → 浏览瀑布流 → 行为画像 → 个性化推荐 → 提问检索 → AI 辅助创作 → 管理员发布 → 回到首页
```

每一步都落在“用户能感知的功能变化”和可核对的业务结果上。本版只考虑功能覆盖、操作顺序和验证条件，不限定演示时长，不用未经实测的性能数字作为结论。

主线包含两个相互衔接的闭环：**行为 → 画像 → 首页推荐**，以及 **检索 → 创作 → 审核 → 公开访问**。不要暗示创作 Agent 已经读取兴趣画像；两者是否共享数据，以真实调用链路为准。

## 二、演示前准备

| 项 | 内容 |
|---|---|
| 设备 | Android 真机 + 管理端浏览器；需要展示跨端一致性时，再打开 Web 用户端 |
| 版本 | 本地 master、手机安装包、服务器发布版本分别核对；切换源码分支不等于手机安装包已更新 |
| 账号 | 普通用户 A（主演示）、普通用户 B（验证公开访问、评论、私信、通知）、管理员；彩排与正式演示尽量使用不同普通账号 |
| 数据准备 | 已发布演示作品 1029～1038，详见第五节；另准备一篇待审核备用作品，记录其 ID，不把它冒充现场创建的作品 |
| 环境确认 | Java/Python 健康、画像同步任务成功、公共首页推荐接口正常；MCP 单独核对实际运行版本和授权连接 |
| 素材 | 一组可上传的图片、明确的创作事实素材、检索问题、评论和私信测试文本 |
| 数据证据 | 画像前后版本、推荐响应、作品 ID 与状态、审核记录；只展示必要字段，不展示密码、令牌或服务配置 |

### 关键依赖（演示前必须确认）

- 2026-11-12 核对的 master `40e27eb` 已接通 Android 公共首页首屏推荐；后续翻页仍走普通 Feed，关注流是独立入口。
- 画像异步更新。必须确认新的行为进入画像，再刷新公共首页；不能把“点完赞立即刷新”当成必然生效的操作。
- 推荐响应检查 `strategy`、`reason`、`profile_version`、`fallback`；仅 `fallback=0` 或“出现一张咖啡卡片”不足以证明使用了本次更新的画像。
- 画像使用标题关键词规则和行为权重，不读取独立标签字段，也不调用 Agent 提取主题。推荐候选目前来自最近 50 篇公开作品。
- 新账号冷启动、个性化关闭、画像不可用与正常个性化是不同状态，演示前记录当前状态。

## 三、演示脚本（5 步）

### Step 1 · 注册登录 + 访问瀑布流

**操作**：打开 App → 注册一个新账号（或直接登录）→ 进入首页 → 上下滑动瀑布流浏览几张。

**台词**：
> "这是我们的社区首页，双列瀑布流。用户登录后就能浏览作品，图片有预加载，滑动很流畅，内容连续不断。"

**验证点**：瀑布流正常加载、图片显示、滑动与续页可用。

**补充操作**：打开图片作品、切换多张图片、返回列表继续浏览；打开一篇现有视频作品检查播放。进入作者页并关注，再切到“关注”流验证来源变化。不要用个人画像解释关注流。

**注意**：现场流畅只能说明这次使用体验正常；没有对照实验就不声称预加载提升了某个百分比。

---

### Step 2 · 行为 → 画像 → 推荐

**操作**：
1. 记录 A 的画像主题、得分、版本和当前推荐结果；确认个性化推荐已开启。
2. 打开作品 1029、1030、1032，浏览、停留并点赞；确认原先未点赞，避免操作成取消点赞。离开详情页，让停留行为按实际客户端逻辑上报。
3. 检查本次行为记录；等待同步任务成功，再进入兴趣画像页查看更新后的主题得分和版本。有历史记录时，打开画像历史进行前后对照。
4. 刷新公共首页，核对推荐响应使用的画像版本及策略，并观察作品顺序与推荐理由。
5. 1031、1033 保留为未主动操作的相关候选；它们不保证一定出现，推荐还受候选范围、作者与主题多样性等因素影响。
6. 额外演示关闭与恢复个性化推荐，检查请求策略的变化；再按实际页面入口展示主题/作者偏好调整及恢复。完成后恢复正式演示需要的设置。

**台词**：
> “浏览和点赞会异步进入兴趣画像。画像更新后刷新公共首页，系统会结合兴趣和推荐规则重新排列首屏内容。”

**验证点**：
- 行为属于当前演示账号，画像确实更新，推荐使用相应版本且走个性化策略。
- 观察美食主题得分及结果顺序；占比不一定上升，尤其账号原先已高度偏向美食时。
- 同步或推荐失败时分别展示已完成的环节；不能把普通 Feed 降级结果当成个性化成功。

**数据佐证（可选，不报具体数字）**：行为事件已写入、画像主题得分变化。

---

### Step 3 · 提问 → 站内检索 → 上下文辅助

**操作**：
1. 在搜索页输入“咖啡”，先展示普通搜索结果，再使用该页面实际提供的 AI 回答入口；如需展示通用 Copilot 的工具检索，则从通用入口提问“帮我找站内关于咖啡的作品，归纳各自适合参考的内容”。这两条入口分别验收，不混称为同一次调用。
2. 展示生成过程与最终回答，打开一条来源引用，核对标题、作品 ID 和原文。
3. 进入一篇作品详情，展示作品总结；再打开详情 Copilot，让它“结合这篇作品拟一条具体评论”。
4. 检查评论提案，先取消一次，确认评论列表没有新增；再次生成并确认后，检查评论真实出现且归属当前用户。

**台词**：
> “站内检索回答附带参考作品，用户可以回到原文核对；详情页助手则结合当前作品生成评论提案，由用户确认后执行。”

**验证点**：普通搜索、AI 回答、来源跳转、作品总结、详情评论提案分别有真实结果；提案取消不写入，确认后才执行。带引用不等于绝不会产生错误，仍需核对原文。

---

### Step 4 · 创作 + AI 辅助创作 + 管理员发布

**操作**：
1. 使用唯一标题，例如“答辩演示·咖啡阅读记录·本次编号”；记录创建后的作品 ID，后续始终核对同一条作品。
2. 选择图片、检查预览与顺序，填写事实素材，例如“拿铁口感偏甜，环境安静，适合阅读；不补充店名、价格和地址”。
3. 展示 AI 辅助创作及生成过程，核对标题/正文填入结果；演示撤销恢复，再重新采纳需要的内容。创作页内联辅助可能自动填入可编辑草稿，不要把它与 Copilot 的确认提案机制混为一谈；自动填入不代表自动发布。
4. 保存草稿，返回“我的作品”重新打开，确认文本和媒体保存成功。补充展示创作场景 Copilot 修改草稿提案；以实际入口为准确认执行。
5. 提交审核，确认作品状态为待审核；用 B 检查该作品尚不能作为公开作品访问。
6. 管理员在独立浏览器登录，按作品 ID 找到待审核内容，点击“获取 AI 建议”，核对风险、建议动作与理由。
7. 人工检查内容并填写审核理由，确认通过；查看已发布状态以及审核记录中的作品 ID、操作者、前后状态与理由。
8. 使用独立备用作品补充演示驳回及作者查看驳回理由。不要用主线已发布作品临时演示破坏性的状态变化。

**台词**：
> "用户用 AI 辅助写草稿，提交后进入审核。管理员这边会看到 AI 给出的风险建议作为参考，但最终由管理员拍板，确认后发布。"

**验证点**：草稿 → 待审核 → 管理员看到 AI 审核建议 → 发布成功（状态变为已发布）。

---

### Step 5 · 公开访问与内容互动闭环

**操作**：
1. 用 B 刷新公共流或搜索唯一标题，打开刚发布作品，核对 ID、正文、图片和作者。
2. B 对该作品点赞、收藏并评论；在收藏列表中重新找到作品。A 查看评论和互动通知，回复 B，再由 B 查看回复结果。
3. 展示通知已读状态或未读角标变化。A/B 必须是可登录的真实演示账号，不能使用导入时创建的不可登录样本作者。
4. 如展示跨端一致性，在 Web 用户端登录对应账号，查看同一作品、收藏或评论；不假定 Web 首页也使用了 Android 同样的个性化接口。

**台词**：
> “这条作品经过辅助创作和人工审核后，其他用户已经可以访问和互动。前面的行为画像影响内容发现，这里的审核流程保障内容进入公开社区。”

**验证点**：同一作品从待审核变为其他用户可访问，互动结果与通知可核对。发布不保证进入个性化首屏，不能仅凭首屏没看到就判断发布失败。

---

## 四、注意事项

1. **不混淆机制**：画像是标题关键词规则与行为加权；推荐是确定性的 Skill 组合；Agent 工具调用与外部 MCP 接入分别展示。
2. **核对账号和状态**：彩排后检查点赞、关注、个性化开关、屏蔽偏好及作品状态，避免复用已改变的前置条件。
3. **异步步骤以结果为准**：行为上报成功、画像生成成功、推荐读取新版画像是三个检查点。查看画像不会自动触发重算；如手动触发维护，明确说明。
4. **不夸大权限与事实能力**：AI 审核是建议；引用需要核对；草稿填入、用户确认、提交审核和公开发布是不同状态。
5. **备用链路可继续且如实标注**：准备检索/生成彩排记录、待审核备用作品、已发布备用作品。切换时明确说明来源及作品 ID；用备用内容跑通后续功能，不等于前面的失败步骤已验收。
6. **只展示必要数据**：日志与后台证据不展示凭据、无关私信或其他用户的隐私。只用 A/B 演示账号验证消息功能。
7. **不以异常制造为主线**：网络中断、版本冲突、重复提交等使用独立测试内容或已有验证记录；不停止共享服务器、不清空真实数据。

## 六、主线之外需要补充的功能流程

以下是功能覆盖补充，不按演示时长取舍。只有看到对应业务结果才勾选完成；界面存在、服务存活或只读到代码不能代替实际验收。

### A. 私信与 Agent 消息处理

1. 使用可登录的 A/B，建立实际私信会话；B 向 A 发送明确的测试问题。
2. A 查看并手动回复，B 核对收到的内容，证明基础消息链路可用。
3. 在支持该能力的消息助手或通用 Copilot 入口，让 Agent 总结当前账号的会话，再生成回复提案。
4. 核对会话对象与内容，取消时不发送，确认后由 B 验证实际收到。若演示多会话提案，每个接收人都必须是明确准备的测试账号。
5. 记录实际使用的平台和入口，不把 Android 的能力自动套用到 Web 用户端。

### B. 评论自动回复与 Skill 业务流程

1. 在 A 自己的演示作品上设置一条明确的问答规则，例如“这篇分享是否包含店铺地址？”→“这篇是记录方法示例，没有提供具体店铺地址。”
2. 如使用 AI 辅助生成规则，先检查建议，再保存规则；生成文本不等于规则已生效。
3. B 发布命中场景的一级评论，查看自动回复是否出现；再发一条无关评论，观察是否避免不相关回复。
4. 查看规则启用状态，展示关闭/恢复入口；实际触发与否按真实结果记录，不保证模型每次判断一致。
5. 对应说明业务流程：规则准备 → 场景判断 → 回复执行 → 结果查看。与画像推荐的 `profile_insight → candidate_recall → feed_rank` 区分，后者无需模型自由规划。

### C. 外部 MCP 接入

这一步需要真正支持 MCP 的外部客户端。只在 App 中使用 Copilot，不能算完成 MCP 演示。

1. 确认 MCP 服务实际加载的版本、连接地址及客户端配置。此前检查发现其进程启动早于最新发布，正式演示前重新核实，不能只看发布目录。
2. 用演示账号完成授权，确认授权身份与客户端可见的工具列表；不要在投屏中展示令牌。
3. 调用 `search_posts` 搜索“咖啡”，再调用 `get_post` 读取其中一条作品，核对返回作品 ID。
4. 明确要求外部助手创建一篇带“MCP演示”唯一标题的草稿；通过 `create_post_draft` 创建，再用 `list_my_posts` 或 App 的“我的作品”确认同一条草稿。
5. 调用 `update_post_draft` 修改内容并核对；如需展示媒体上传，使用本地演示图片和 `upload_media`，再把返回的媒体引用用于草稿。
6. 明确确认后调用 `submit_post_for_review`；管理员按前述流程审核，普通用户验证公开访问。MCP 提交审核不等于拥有管理员发布权限。
7. 需要展示撤回时，使用专用 MCP 演示作品调用 `withdraw_post`，再验证状态与公开可见性变化，不撤回主线作品。

**验证点**：外部工具调用 → 同一业务系统中的真实状态变化。保留工具名、作品 ID 和结果，不将内部 Python 函数调用称为外部 MCP 调用。

### D. AI 任务交互、流式展示与历史

1. 分别观察搜索、总结、创作等实际支持流式输出的入口，展示内容逐步出现以及最终完成状态；不把所有 AI 功能都描述为流式。
2. 在实际允许离开的页面启动任务后返回列表，进行普通浏览或互动，再回到任务/历史入口查看状态和结果。以设备实际结果验证请求隔离，不仅展示加载动画。
3. 在任务列表或历史入口查看任务归属、完成/失败状态，以及结果能否重新打开；如有取消、重试入口，再用专用测试任务验证。
4. 区分页面切换后的恢复与应用被杀死后的恢复。未经验证，不声称所有任务都能跨进程恢复。
5. 有失败时查看提示并验证用户已有草稿仍在；不要通过关闭线上服务制造失败。

### E. 个人中心、收藏、关注与内容管理

1. 修改演示账号昵称、简介或头像，保存后重新进入个人页核对。
2. 查看关注/粉丝列表，打开作者公开页；关注与取消关注后核对列表和关注流。
3. 收藏作品，在收藏列表打开；取消收藏后重新检查列表。
4. 在“我的作品”检查草稿、待审核、已发布、已驳回等状态；使用专用作品演示编辑与撤回，核对服务器状态。
5. 分享作品链接后由 B 打开，检查落到正确作品；以真机实际可用的分享入口为准。
6. 如需覆盖管理员用户管理，使用独立测试账号验证状态修改及恢复，不禁用 A/B、管理员或样本作者，避免影响其他演示步骤。
